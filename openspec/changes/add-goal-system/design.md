## Context

动机见 `proposal.md` 的 Why，需求契约见 `specs/goal-management/spec.md`。完整的现状调研与行号级引用见 `docs/superpowers/specs/2026-08-15-goal-system-design.md`。

塑造本设计的约束只有三条：

1. 要被统辖的四类对象分散在四个 bounded context（`task_orchestration`、`agent_runtime`、`work_board`、`sessions`），没有任何一个是天然的归属地
2. 三类执行体的终态语义互不一致，且其中一处反直觉：计划的失败允许重跑，因而不是终态；循环的失败是终态
3. 本仓库全部 worktree 共享同一个本地 SQLite 文件，迁移版本号是跨分支的共享资源

## Goals / Non-Goals

**Goals:**

- 目标成为独立聚合根，关联关系单向由目标侧持有，四个执行体 context 零改动
- 达成推导在没有领域事件的前提下始终自洽，不会出现需要人工修复的状态漂移
- 三类执行体的终态判定各自独立且可被穷举测试

**Non-Goals:**

- 不做目标层级（父子目标、目标树）。第一期是平铺结构
- 不给目标引入自己的验证命令或证据链。循环与计划各自已有完整证据链，目标再加一套会与子项验收形成双重判定冲突
- 不做跨项目的目标聚合视图或统计报表
- 不改变任何执行体的状态机、字段或对外接口

## Decisions

### 关联关系由目标侧独占，而非在执行体上加外键列

选择在 `goals` context 内建 `goal_links(goal_id, target_kind, target_id)` 单表，`target_kind` 为枚举。

考虑过的替代方案是给四个执行体表各加一列 `goal_id`。它的正向查询更快，前端拿数据不需要反查。放弃的原因有二：一是要做四处 schema 迁移、四个 context 都得感知目标的存在，边界被咬死；二是在共享同一个 SQLite 文件的前提下，四个迁移版本号比一个更容易与其他分支撞车。

统一关联表还有一个附带收益：将来接入第五类执行体只需增加一个枚举值，不动任何表结构。

### 待验收是派生态，不落库

持久化状态只有草稿、进行中、已达成、已放弃四个。

考虑过把待验收也持久化，配合执行体发布领域事件来推进。放弃的原因是它引入了一类无法自愈的故障：任何一次事件遗漏都会让目标永久停在错误状态，而用户看到的是一个「已经可以验收但按钮点不动」的界面，且没有任何自助修复路径。派生态每次重算，子项一旦回退目标自动跟着回退，不存在这个故障模式。

代价是无法在子项完成的瞬间主动通知用户。这个代价可以接受：目标是低频对象，用户主动打开时看到正确状态即可。

### 进度用拉模式聚合

打开目标时现查四类子项状态。这是上一条决策的必然结果——既然不持久化派生态，就必须现算。

考虑过定时预计算并缓存。第一期不做：目标数量与子项数量都在个位数到两位数量级，现查的成本远低于维护缓存失效的复杂度。

### 三类执行体的终态判定分开实现

计划终态为已完成与已取消；循环终态为已成功、已失败与已取消；看板项终态为完成阶段或已归档。

这个不一致不是疏漏，而是既有语义的忠实反映：计划的状态机里存在从失败回到运行中的迁移，失败的计划运行可以重跑，所以它不是终点；循环的状态机没有这条边。共用一份终态定义会让可重试的失败计划把目标错误地推进待验收，这是本设计最容易被实现者写反的地方，规范里为它单列了场景。

同理，两者的待验收都被既有状态机归为活跃而非终态——子项自己还等着人验收，目标不能宣称待验收。

### probe 定义为 trait，实现落在 infrastructure

`domain/` 与 `application/` 不 import 任何执行体 context。四类子项的状态查询以 trait 形式定义在 `application/ports.rs`，具体实现放 `infrastructure/`，在组合边界注入。

这是「零侵入」承诺的兑现点，也让聚合逻辑成为可用假 probe 穷举测试的纯函数。目标有状态机这一不变量要保护，因此采用完整分层，不走 `work_board` 那种无 `domain/` 的精简形态。

### 会话关联只做人工挂载

会话不参与推导，且不自动挂载。自动挂载会把大量无关短会话堆进目标详情页，让这个视图迅速失去可读性。

## Risks / Trade-offs

**迁移版本号与其他分支撞车** → 落号前查 `schema_migrations` 表与其他活跃分支已占用的号段。这个故障的症状是应用启动崩溃并报「no such table」，酷似真实回归，误诊成本很高，因此必须在实施第一步就处理。

**新建 context 未同步 `openspec/project.md` 的 Bounded contexts 表** → 该表由 `scripts/validate-docs.mjs` 强制与目录严格一一对应，漏改会让 `npm run docs:check` 失败。同一变更内加行。

**失败但可重试的计划让目标长期停滞** → 这是符合语义的行为，工作确实没做完。缓解手段是界面呈现，目标详情必须让阻塞原因一眼可见，而不是只显示一个不动的进度条。

**单个 probe 失败拖垮整个目标查询** → 每个 probe 独立降级为不可解析，聚合逻辑对分母做相应剔除。规范中已为此单列场景。

**拉模式无法主动通知** → 已在决策中接受。若将来需要即时通知，可在不改变持久化模型的前提下叠加一层轮询或订阅，派生态的自洽性不受影响。

## Migration Plan

新增两张表，不修改任何既有表，因此没有数据迁移。回滚即删除这两张表，四个执行体不受影响。

前端两个适配器实现必须同时落地，否则 Web 运行时会出现接口缺失。
