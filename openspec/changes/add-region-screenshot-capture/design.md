## Context

The structured composer currently reaches file OCR through `LocalMediaService.selectAndStageOcrSource()`. The Tauri adapter opens a native picker and hands the chosen path to Rust; the Web adapter returns a truthful unavailable result. Screenshot selection must preserve that boundary while adding a second renderer surface and operating-system screen access.

The project already has reusable pieces for this design: bounded PNG decoding, OCR staging, unified redacted logging, Tauri secondary-window management, and a `surface` query switch in `src/main.tsx`. The capture backend itself is new. The maintained `xcap` crate is selected because its official API captures monitors/regions across Windows, macOS, Linux X11, and supported Wayland environments; its platform limitations will remain typed availability rather than be hidden by fallbacks.

## Goals / Non-Goals

**Goals:**

- Make region capture feel like one local composer action and return a normal `StagedOcrSource`.
- Keep renderer/native isolation, scope ownership, bounded resources, and deterministic cancellation.
- Present the desktop as it looked when capture began, including all supported monitors and HiDPI geometry.
- Make the native workflow testable with injected monitor, window, clock, temporary-storage, and capture ports.

**Non-Goals:**

- No annotation, scrolling capture, delayed capture, clipboard integration, image attachment, or automatic message sending.
- No cross-monitor rectangle; a drag is bound to the monitor where it begins.
- No screenshot control in single-Agent CLI terminal input, matching the existing Local Media controls.
- No shelling out to platform screenshot utilities and no hosted/Web capture fallback.

## Decisions

### 1. The composer receives one high-level select-and-stage operation

`LocalMediaService` gains `selectAndStageScreenshotRegion()` alongside the existing file picker method. The main composer neither manages Tauri windows nor sees monitor metadata, native handles, or paths. The Tauri adapter invokes one start command and receives `StagedOcrSource | null`; the Web adapter returns `null` and reports capture as native-only through availability.

The capture overlay uses a narrower service surface to submit or cancel a run-scoped selection. It is still implemented by the runtime Local Media adapter, so no React component imports Tauri APIs.

Alternative considered: let the composer enumerate monitors and orchestrate windows. Rejected because it moves native lifecycle, display identity, and privacy-sensitive metadata into ordinary React state.

### 2. Capture a monitor snapshot before showing opaque selection windows

Rust hides every visible VaneHub window, snapshots a bounded monitor inventory through the native capture adapter, holds each monitor as a run-owned in-memory image and encoded PNG, then opens one undecorated always-on-top selection window per monitor. Each window is positioned with the monitor's logical origin and size and displays its matching frozen screenshot as the background.

This avoids relying on transparent-window support, which differs across WebView2, WebKitGTK, and WKWebView, and prevents VaneHub or its selection overlay from appearing in the captured pixels. It also makes the committed crop deterministic: the native layer crops the already captured snapshot rather than taking a second screenshot after pointer-up.

The run is bounded to eight monitors, 48 million total pixels, 120 seconds, and one active capture application-wide. A monitor that exceeds the aggregate budget fails before any overlay opens.

Alternative considered: transparent overlays followed by a second native capture. Rejected because transparency is not uniformly supported and compositor timing can capture the overlay itself.

### 3. Serve frozen snapshots through an opaque custom protocol

The Tauri builder registers a `vanehub-capture` protocol. A selection window loads its image from a URL containing only an opaque run id and display token. The protocol handler verifies that the requesting webview label belongs to the same run and display, looks up the run-owned PNG, returns `image/png` with `no-store`, and never accepts a filesystem path.

On Windows the runtime-specific localhost URL form is generated by a small frontend helper; macOS/Linux use the scheme URL form. No PNG bytes are serialized through `invoke`, and no temporary path enters React state.

Alternative considered: base64 PNG data in the command response. Rejected because 4K/multi-monitor captures would create large JSON allocations and duplicate sensitive pixels in frontend debugging surfaces.

### 4. Native state owns validation, completion, and cleanup

A capture registry holds at most one `CaptureRun`: initiating main-window label/focus state, hidden application windows, deadline, in-memory monitor snapshots, opaque display tokens, overlay labels, and a one-shot result channel. Overlay submit/cancel commands include the run id and display token. Rust validates finite logical coordinates, minimum size, bounds, scale factor, overflow, active run, and calling overlay label before cropping.

Every terminal path destroys all overlay windows, drops every run-owned in-memory snapshot, restores all application windows that capture hid, focuses the initiating window, resolves the waiting command exactly once, and clears registry ownership. Captured pixels are not persisted. If a future platform adapter cannot avoid temporary files, it must use the bounded local-media temporary root and preserve the same cleanup guarantees before it can replace the in-memory adapter.

### 5. The selected crop reuses OCR admission and review

After a valid commit, Rust crops the frozen in-memory monitor image, re-encodes only the selected rectangle, and feeds those bytes through the existing OCR artifact/staging admission. Full-monitor snapshots are dropped before returning the `StagedOcrSource`. The existing `startOcr`, operation ownership, polling, editable review, append, overflow, and discard behavior remain unchanged.

The frontend controller shares one helper for “obtain staged source then start OCR,” so file OCR and screenshot OCR cannot drift in ownership or error handling.

### 6. Errors and logs are metadata-only

The native domain defines stable capture codes for unavailable backend, permission denied, no displays, busy, invalid selection, budget exceeded, timeout, and capture failure. Raw `xcap`, WebView, monitor, and filesystem errors are reduced at the infrastructure boundary. Unified diagnostics contain only outcome, stable reason, duration bucket, monitor-count bucket, and selected-dimension bucket.

The custom protocol returns generic 404/410 responses and no diagnostic body. Frontend errors use localized stable codes; cancellation is a normal `null` outcome.

### 7. Verification uses ports and a desktop-only deterministic activation

Rust application tests use fake monitor snapshots and window ports to cover coordinate conversion, multi-monitor isolation, races, timeout, cleanup, and redaction without reading the real desktop. Component and Web Playwright tests exercise visibility, accessibility, disabled states, cancellation, and OCR review through deterministic service doubles.

The desktop-E2E feature adds a deterministic screenshot fixture activation that supplies synthetic monitor pixels to the same application service and creates real Tauri overlay windows. A separate opt-in live capture check records Windows, macOS, Linux X11, and Linux Wayland results independently and never uploads captured pixels.

## Risks / Trade-offs

- [Wayland portals/compositors can deny or constrain capture] → Keep backend availability typed, test X11 and Wayland separately, and never shell out to compositor-specific tools.
- [macOS requires Screen Recording permission] → Map denial to a localized permission action and verify first-run/retry behavior on a macOS runner or manual qualification host.
- [Full-monitor frozen images consume memory briefly] → Cap count/pixels/time, keep ownership inside one capture run, and drop every snapshot on all terminal paths.
- [Display topology can change during selection] → Bind to the start snapshot; close with a typed stale-display failure if the overlay or display witness no longer matches.
- [Custom protocols expand the local attack surface] → Accept only opaque registry tokens, bind requests to webview labels, deny traversal/query payloads, return `no-store`, and keep the registry single-run/bounded.
- [The frozen desktop does not update while selecting] → This is intentional and deterministic; the overlay describes that the user is selecting from the captured moment.

## Migration Plan

1. Add the dependency and Linux build prerequisites without enabling a user-visible route.
2. Land native domain/application/infrastructure behind additive commands and deterministic tests.
3. Add the overlay surface and Tauri/Web service methods.
4. Add the composer action and localized copy, then run Web and real desktop verification.
5. Rollback is additive: remove the screenshot action and commands; existing file OCR/profile data require no migration.
