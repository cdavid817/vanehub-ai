Confirmed sufficient as-is, no extension needed: `platform::process::ProcessRequest`/`ProcessAdapter` gives explicit-argument (never shell-concatenated), timeout, cancellable, output-bounded subprocess execution plus an `audit_command` logging hook; `platform::filesystem::BoundedFilesystem::new(root)` + `resolve_existing`/`resolve_with_existing_parent` gives traversal/symlink-escape-safe path resolution for read vs. write.

The accumulator (task 2.2/3.x) supports both via `finish(index)` and `finish_all_pending()`.

## 5. Infrastructure: the tool-use loop and approval blocking

- [x] 5.1 `execute()` rewritten as a bounded loop (`MAX_TOOL_ROUND_TRIPS = 25`). Refactored `build_request_body` to take pre-converted `&[Value]` turns instead of `&[AgentMessage]` (both providers gained a `history_to_turns` function for the one-time initial conversion) specifically so the loop can `turns.extend(build_reply_turns(...))` each iteration without re-deriving from message history. Intermediate tool turns are in-memory-only (design.md Decision 2) — never written through `ConversationHistoryPort`.
- [x] 5.2 Approval blocking: `ManagedApiGeneration` gained `pending_approvals: Arc<Mutex<HashMap<String, mpsc::Sender<ToolApprovalDecision>>>>`. `await_approval()` registers a channel, emits `AwaitingApproval` (via `GenerationProcessEvent::ToolUse` with `status: "awaiting_approval"` — reused the existing `ToolUse` variant as the adapter's internal signal rather than adding a new one), then polls `rx.recv_timeout(200ms)` against the cancellation flag in a loop rather than an unbounded wait — `stop_generation` still works while a call awaits approval. `ToolApprovalPort::resolve` looks up the managed generation by `process_id`, removes and sends on the matching sender.
- [x] 5.3 Round-trip cap: exceeding it returns non-retryable `Failed`.
- [x] 5.4 No change needed to `AgentMessage.tool_use`'s shape. Discovered and reused existing infrastructure: `GenerationEventHandler::tool_use()` (`service.rs`) already converts a simple `ToolUseBlock` + status string into a full `ToolLifecycleEvent` *and* persists it via `sessions.append_tool_use()` — extended its status-string mapping with one line (`"awaiting_approval"` → the new phase) so the adapter never needs to hand-construct a full `ToolLifecycleEvent` with observability fields itself.
- [x] 5.5 9 new adapter tests: `await_approval` approved/denied/already-cancelled; `execute_tool_call` unknown-tool/no-workspace-folder/routes-shell-and-file-correctly; `ToolApprovalPort::resolve` unknown-process/unknown-call-id. Full end-to-end loop tests (real HTTP round-trip with tool calls) were **not** added — consistent with this codebase's existing precedent of not mocking a live HTTP server for the CLI or Phase 1 API adapters; the loop's *shape* is covered by these unit tests plus the wire-format tests in section 3, and its live behavior is covered by the manual smoke test (8.6).
- Also fixed a real bug found during this work: `ProcessOutput.success()` was called after partially moving `output.stdout`/`output.stderr` out — fixed by capturing `success` before the move.
- Also corrected a status-string mismatch caught by re-reading the CLI parser: the "running" tool phase uses status string `"running"`, not `"pending"` as first written — fixed to match `providers/output.rs`'s established convention exactly.

## 6. Tauri commands and interface layer

- [x] 6.1 **Design correction made during implementation:** the proposal assumed the frontend would pass `process_id` directly, matching an early draft of `ToolApprovalPort`. But the established pattern (`stop_generation`) has the frontend pass `session_id` only, with the *backend* resolving the active `process_id` internally. `AgentGenerationPort::cancel` existed for this but is destructive (cancels the generation) — added a new non-mutating `AgentGenerationPort::active_process_id(session_id)` instead, implemented in `InMemoryGenerationCoordinator` and wired into `AgentRuntimeApplicationService::resolve_tool_approval(session_id, call_id, decision)`. New Tauri command `resolve_tool_approval` takes `{sessionId, callId, approved: bool}` — a plain `bool` rather than a string decision, so there's no invalid-string case to validate.
- [x] 6.2 Registered in `commands/registry.rs`; DTO (`ResolveToolApprovalInput`) + mapper (`tool_approval_decision(bool) -> ToolApprovalDecision`) follow the `register_api_agent` pattern exactly.
- [x] 6.3 Compiler-guided exhaustiveness fixes: `ToolLifecyclePhase::AwaitingApproval` required one match arm addition in `service.rs`'s telemetry-span-terminal-status logic (grouped with `Started`/`Updated` as non-terminal). `AgentGenerationPort::active_process_id` required implementations in `FakeWorld` and `TerminalWorld` (both test doubles) plus `InMemoryGenerationCoordinator` (real).

### Note on an environment issue discovered (not a code defect)

While running the full test suite, `cargo test --lib` at default parallelism appeared to hang. Root cause: a machine-wide `all_proxy=socks5://127.0.0.1:8888` environment variable (the same one documented in `add-custom-agent-registration/tasks.md` 9.5c for Playwright) interferes with pre-existing, unrelated MCP HTTP-relay tests that spin up local fixture servers — not any code from this change. Confirmed by running with `--test-threads=1` (surfaced the real MCP test failures instead of an opaque hang) and then with `env -u all_proxy` (819/819 pass at both single- and default-threaded concurrency in ~25s). Run Rust test/clippy/build commands in this repo with `all_proxy` unset.
