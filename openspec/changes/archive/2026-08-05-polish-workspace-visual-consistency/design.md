## Context

This change comes out of an evidence-based walkthrough: the app was actually run (Vite dev server + Playwright/Chromium against the Web/mock adapter), screenshotted across the main workspace, all 9 session tabs, all 14 settings pages, Loop Center, both `futuristic`/`minimal` styles, and two narrow desktop widths (900px, 640px).

Current state:
- `src/styles.css` already defines the shared panel/card token layer (`.ucd-panel`, `.ucd-card`, `.ucd-muted-panel`, etc.) backed by semantic HSL custom properties for both registered styles.
- The workspace shell (`src/main-layout/*`) and all 14 settings pages (`src/settings/pages/*`) consistently apply that shared layer.
- `src/loop-center/loop-center.tsx` and its child views render the same three-column shape (nav / main / inspector) but without any of the shared panel/card treatment — confirmed in both `futuristic` and `minimal` screenshots.
- `src/settings/pages/mcp-page.tsx` groups servers under plain-text `-- 用户配置 --` / `-- 项目配置 --` separators instead of the existing section-header pattern (`SectionPanel`/similar in `src/settings/pages/page-parts.tsx`) used elsewhere, e.g. Basic Settings.
- The workspace top bar's search input is present at desktop width but is absent (with no replacement control) at the ≤900px breakpoint that `main-layout-ui` already treats as meaningful for the activity bar and session sidebar.
- The notification framework already defines a "toast expires after its configured duration" scenario, but the toast observed in this walkthrough remained visible across several subsequent in-app tab switches.
- The Agent Terminal's Web/mock "local CLI unavailable" notice currently prints one Chinese line and one English line back to back for the same event.
- The Agent Configurations page's OnePiece tab (`onepiece-configuration-panel.tsx`) wraps its content in `SectionPanel`'s default bordered "card" variant, while its three sibling tabs (`agent-global-config-panel.tsx`, backing Claude Code/OpenCode/Codex CLI) render flat with no outer card — confirmed by screenshotting all four tabs side by side in both styles, where only OnePiece shows a visible outer border/shadow. The same diff also showed OnePiece has no local "search saved profiles" input, unlike its three siblings.
- The Skill Management page's `LifecycleSkillRows` (`skill-card-list.tsx`, rendered for the "全部"/"未分配" nav views) wraps its rows in `border border-border bg-background`, while `SkillSelectionPanel` (rendered for a specific-Agent view, same file) and the empty state both use `.ucd-panel` — confirmed by screenshotting both views in both styles, most visible in `minimal` where `.ucd-panel`'s tinted background clearly separates from the white page while the plain `border-border bg-background` box barely registers against it. `git log -p` on this file shows both variants were introduced in the same commit (`14b67ca`, "improve skill management and mount safety"), so this reads as an oversight within that refactor rather than a deliberate choice.
- The Skill Management page's filter toolbar (`skill-filter-toolbar.tsx`) has category/source/status/sort dropdowns but no free-text search input, even though `SkillInventoryFilters.query` exists, is consumed by `filterGlobalSkillInventory`, and is explicitly reset by the toolbar's own "清除筛选" button — and the translation keys `skills.filters.search`/`skills.filters.searchPlaceholder` already exist in all 5 locales but are unused anywhere in `src`. `git log -p` on the same file resolved this: a local search input existed in the original implementation and was deliberately removed in the same `14b67ca` commit that introduced the drift above, as part of consolidating `category`+`query` props into a unified `filters` object alongside new source/status/sort filters. Given this was a real, intentional design change (not a bug), the user was asked directly whether to restore it before any code was written; they confirmed restoring it.
- The Prompt Hook page's four dialog/overlay states are hand-rolled: `prompt-hook-dialogs.tsx`'s `Modal` (backing preview/delete-confirm/create-edit) and `prompt-hook-lifecycle-panel.tsx`'s overlay both use a raw `<div className="fixed inset-0 ...">` with no `role="dialog"`, no `aria-modal`, no Escape handling, and no focus trap — confirmed with the same scripted-probe method used for the MCP dialog fix (task group 12): pre-fix, `page.getByRole("dialog")` resolved to 0 elements and pressing Escape while the create dialog was open left it visibly open.
- A follow-up layout-focused pass on the same page (user asked specifically about "布局"/layout, after the dialog-accessibility round) found: (1) `prompt-hook-filter-toolbar.tsx`'s 5-column grid activates at `lg` (1024px), but at that width the settings content column doesn't have enough room — screenshots at 1024px show the search input's own placeholder text truncated mid-word; the layout is fine both below 1024px (stacked) and at/above 1280px (enough room). (2) The "当前显示 N / M" result-count summary in `prompt-hooks-page.tsx` renders after the entire card list rather than near the filters, so adjusting a filter doesn't show updated feedback until scrolling past all currently-visible cards — confirmed by screenshotting the bottom of the page, where the summary sits squeezed between the last card and the trace panel.
- SSH Connections' add/edit dialog (`ssh-connection-form.tsx`) has the same hand-rolled-overlay gap as MCP/Prompt Hook: no `role="dialog"`, no `aria-modal`, no Escape handling. It also has two issues unique to this page: (1) `ssh-connection-card.tsx`'s test-status badge uses `ucd-status-info`, a class that doesn't exist anywhere in `src/styles.css` (confirmed by grep — zero matches outside this one usage site) — a computed-style probe showed the badge's background is `rgba(0, 0, 0, 0)` (fully transparent) in both the "not-tested" and "succeeded" states, meaning the status color-coding has never actually worked. (2) The form computes and displays validation errors for all seven fields unconditionally from initial state, so opening "新增 SSH 连接" on a blank form immediately shows every field as invalid before the user has typed anything — confirmed by screenshot.
- Execution Observability (`observability-settings-page.tsx`) has four sibling `SectionPanel`s (本地时间线/OTLP 导出/采集与隐私/MCP 观测能力). Three nest exactly one single, static info box each — the established "acceptable" shape (task group 17's SSH note). The fourth, "MCP 观测能力", nests a **repeated** grid of four per-agent `.ucd-panel` capability chips — the actual anti-pattern shape, confirmed by full-page screenshot. Separately, this section is also the only one of the four with no `icon` prop, so its header has no icon avatar where its three siblings all do — visible in the same screenshot, a smaller, unrelated inconsistency noticed while fixing the nested card.
- Usage Statistics (`usage-statistics-page.tsx` and its `usage/` sub-components) has the same nested-card shape in two places: `usage-trend.tsx`'s two `TrendLine` boxes and `usage-agent-breakdown.tsx`'s per-agent rows, both `SectionPanel`-wrapped — confirmed by screenshot. A third sub-component, `usage-accounting-note.tsx`, also nests two boxes inside its `SectionPanel`, but they're a fixed, differently-shaped pair (a wide note, a narrow timestamp) rather than a repeated list — judged the same "acceptable" shape as task group 17's SSH note and left alone. Separately, the page's two-column grid (trend chart next to agent breakdown) has no `items-start`, so default `stretch` forces the shorter column to an artificially tall, mostly-empty height when there are few agents — visible in the same screenshot as a large empty gap.
- Plugin Integrations (`plugin-integrations-page.tsx`) has the exact same nested-card shape as Extensions: its "内置集成" list is a `SectionPanel` card wrapping independently-bordered `.ucd-panel` cards — confirmed by screenshot. Unlike Extensions, this page has no dialog anywhere (no sub-directory, no modal code) and its `statusTone()` already maps the status **value** (not translated text) to tone correctly, so it doesn't have the `StatusPill` bug either — the nested card is its only issue.
- Extensions' install-preview dialog (`extensions-page.tsx`'s `InstallPreview`) is a *partially* hand-rolled dialog — unlike every other one fixed this change, it already has `role="dialog"` and `aria-modal="true"` set correctly (the same "static attributes right, interactive behavior missing" shape already noted for `cli-conflict-dialog.tsx` in decision 12). A probe confirmed the gap: on open, `document.activeElement` stayed on the trigger button behind the dialog (focus never moved in), and Escape did not close it. Separately, its framework list nests `.ucd-panel` cards inside a `SectionPanel` card — confirmed by screenshot showing a clear double border in `minimal` style, the same shape as the Basic Settings advanced-config case (decision 8). Separately again, `page-parts.tsx`'s shared `StatusPill` component infers its color by checking whether the **already-translated** status string contains the English substrings `"Disabled"`, `"Error"`, or `"Update"` — since this app's primary locale is zh-CN, translated strings like "异常" (error) or "当前环境不支持" (unsupported) never match, and the ternary's fallback is `"success"`. A screenshot confirmed the "当前环境不支持" badge rendering green. `StatusPill` has a second caller, `sdk-page.tsx`, with the exact same bug (its "错误"/error and "有可用更新"/update-available strings don't match either) — found via grep while scoping the fix, not something the user asked about this round.

## Goals / Non-Goals

**Goals:**
- Bring Loop Center's layout to the same shared panel/card token treatment already used by every other page, in both registered styles.
- Give the MCP settings page's account-scope group headers the same section-header treatment used elsewhere in Settings.
- Keep the workspace top bar search reachable (rendered, or exposed through an equivalent accessible control) at widths at or below 900px instead of disappearing.
- Make toast auto-dismiss timing independent of subsequent in-app navigation.
- Reduce the Agent Terminal's Web-mock "local CLI unavailable" notice to a single localized line.

**Non-Goals:**
- No new design tokens, colors, or a third registered style — this only applies tokens that already exist in `src/styles.css`.
- No functional/data changes to Loop Center, MCP server management, notifications, or Agent Terminal behavior — these are visual/structural and lifecycle-timing fixes only.
- No redesign of the responsive breakpoint system — reuse the existing 900px/640px breakpoints `main-layout-ui` already defines.
- No backend/Rust changes, no new Tauri commands, no SQLite changes.
- Not a full accessibility or full responsive audit — scoped to the specific gaps found during this walkthrough.

## Decisions

1. **Loop Center panel treatment**: wrap the three columns (循环工程 nav / main content / 检查器) with the same `.ucd-panel` / `.ucd-muted-panel` / `.ucd-card` utility classes already used by `src/main-layout/*` and `src/settings/pages/*`, rather than introducing Loop-Center-specific classes.
   - *Alternative considered*: bespoke Loop Center panel styling — rejected, it would create a second visual pattern for the same concept and contradicts the existing "shared tokens, not page-local hardcoded palettes" rule.

2. **MCP settings group headers**: replace the raw `-- 用户配置 --` / `-- 项目配置 --` strings with a left-aligned `border-b` label + count row, matching the divider idiom `page-parts.tsx`'s `SectionPanel` already uses for section headers and the label+count pattern the session sidebar already uses for its pinned group.
   - *Alternative considered*: wrap each group in a full `SectionPanel` — rejected during implementation once it became clear `SectionPanel` is a bordered card wrapper meant for whole sections; wrapping an already-card-based server grid in it would reintroduce the exact nested card-in-card problem this change fixes elsewhere.

3. **Top bar search at ≤900px**: keep the control reachable through the layout's existing responsive mechanism, either by letting it shrink/reflow instead of disappearing, or by collapsing it to an icon-triggered control consistent with this app's existing icon-only control conventions (translated accessible name/tooltip, per the icon-backed-actions rule already in `visual-design-system`). The exact mechanism is an implementation choice captured in tasks.md; the spec only pins the outcome (search stays reachable, not removed).
   - *Alternative considered*: leave it hidden but add a help-text pointer — rejected, adds friction instead of removing it.

4. **Toast dismiss resilience**: toast timer/creation state must live at the notification provider level (already app-wide, per `notification-system`) rather than in a component that can remount on route/tab change and reset its timer. Before changing code, reproduce the lingering behavior directly (manual timing, not just screenshot cadence) to confirm this is a timer-ownership bug rather than an artifact of how the walkthrough was paced.
   - *Alternative considered*: shorten the configured duration — rejected, that would mask a possible ownership bug rather than fix it if one exists.

5. **Agent Terminal Web-mock message**: consolidate to a single active-locale string. Implementation found the duplication came from two independent writers into the same terminal buffer — a proper localized banner (`agent-terminal-tab.tsx`) and a separate hardcoded English mock-`output` event (`web-agent-client.ts`) — so the fix removed the redundant hardcoded event rather than adding new translation keys.
   - *Alternative considered*: keep both lines for "clarity" — rejected, it reads as duplicated content and the localized banner alone already states the same notice.

6. **Session info panel rows**: replace the `Field`/`UsageMetric` components' own `border + bg` wrapper in `src/main-layout/session-info-panel.tsx` with unframed rows (dividers or spacing only) inside the existing `ucd-muted-panel` container, matching project.md's existing "no nested card-in-card" rule.
   - *Alternative considered*: remove the outer `ucd-muted-panel` instead and keep per-field cards — rejected, the outer grouping is what visually ties related fields together as one section; the inner per-field borders are the redundant layer.

7. **Session sidebar secondary controls**: consolidate the always-visible "批量管理"/"归档" row (`src/main-layout/session-sidebar.tsx` line 168) into a compact overflow control (e.g. a kebab menu or merged into the view-switch row), so these session-scoped organization controls stay reachable without permanently costing a full-width row in a 220px-wide column.
   - *Alternative considered*: shrink the session sidebar's minimum width further — rejected, `main-layout-ui` already fixes 220px as the baseline width and floor of the resizable range; consolidating controls doesn't require renegotiating that.

8. **Basic Settings advanced-config nested cards**: add a `"plain"` variant to `SectionPanel` (`src/settings/pages/page-parts.tsx`) that renders the icon/title/description header with a bottom divider instead of its own border/background/rounding, and switch `NetworkProxySection`, `DataManagementSection`, `LogManagementSection`, and the locally-defined `NodeEnvironmentPanel` (all four only ever rendered inside the "高级配置" disclosure) to it.
   - *Alternative considered*: remove the outer `SettingsDisclosure`'s own border instead, letting the four inner cards stand alone — rejected, the outer border is what visually groups "advanced" as one collapsible unit; the inner cards were the redundant layer, not the outer one.

9. **Folder-openers disclosure duplication**: replace `FolderOpenersSection`'s local `<details>`/`<summary>` implementation (`src/settings/pages/folder-openers-section.tsx`) with the shared `SettingsDisclosure` component already used for "高级配置" and Skills' mount-paths panel.
   - *Alternative considered*: leave both implementations as-is since they look visually close today — rejected, they had already drifted (padding, header typography) and will keep drifting as either one changes independently; one shared implementation removes that risk.

**Investigated and intentionally left unchanged**: the "启用悬浮助手" row's icon and its trailing platform-availability paragraph (`src/settings/pages/floating-assistant-settings-section.tsx`) initially looked inconsistent with the plain "开机自启" toggle next to it. Reading the actual copy showed they're not the same kind of content: the icon mirrors the floating assistant's own branding elsewhere in the app (a feature preview, not decoration), and the trailing paragraph carries one of two distinct dynamic messages (available capabilities vs. Windows-only notice) that "开机自启" doesn't have. No change made.

10. **CLI Management duplicate "全部升级" text**: remove the inert `<span>{t("cli.upgradeAll", ...)}</span>` from the "本地环境检查" info row in `src/settings/pages/providers-page.tsx` — it renders the exact same string as the real header action button one section above, with no independent meaning of its own, and the two `StatCard`s directly below it already carry the row's quantitative summary.
    - *Alternative considered*: keep the text but change it to something distinct (e.g. a conflict count) — rejected as scope creep; nothing in the current data model tracks a value that row would uniquely need, and the simplest fix is removing the redundant duplicate.

11. **CLI Parameters sticky agent picker**: give the left "受管 CLI" `SectionPanel` (`src/settings/pages/cli-parameters-page.tsx`) `sticky top-4 self-start` so it stays visible while the right-hand parameter list scrolls independently past it. `self-start` is required alongside `sticky` — without it, the CSS Grid's default `align-items: stretch` would expand the panel to match the taller right column, leaving sticky positioning with an oversized box that defeats the purpose.
    - *Alternative considered*: also make the bottom "安全参数预览" panel `sticky bottom-*` so the live preview stays visible too — reconsidered during implementation and dropped. A bottom-stuck sticky element activates immediately (unlike top-stuck, which only engages once scrolled past), so it would permanently occupy viewport space even for agents like Claude Code whose 4 parameters already fit without scrolling, trading a real cost for a benefit that only some agents need. The sticky agent picker is the clear, no-downside win; the preview's position is left unchanged.

12. **MCP dialog accessibility**: migrate `mcp-server-form.tsx` and `mcp-import-export.tsx` from a hand-rolled `<div className="fixed inset-0 ...">` overlay to the existing shared `ApplicationDialog` component (`src/components/ui/application-dialog.tsx`), which already provides `role="dialog"`/`aria-modal`/`aria-labelledby`/`aria-describedby`, a focus trap, working Escape-to-close, backdrop-click-to-close, and focus restoration on close. Also added `aria-label` to the server card's enable/disable toggle button, matching the `aria-label` + `title` pairing every other icon-only control in this app already uses.
    - Investigation note: the codebase doesn't universally use `ApplicationDialog` — a handful of dialogs (e.g. `cli-conflict-dialog.tsx`) hand-roll the same static ARIA attributes correctly but without the interactive behaviors (focus trap, Escape, focus restoration) `ApplicationDialog` provides via its own `useEffect`. MCP's two dialogs had neither the static attributes nor the interactive behavior — confirmed by a scripted check: the add-server form's container had no `role` attribute at all, and pressing Escape while it was open did not close it. `ApplicationDialog` is the most complete pattern already available, so it's the target rather than replicating the partial hand-rolled pattern.
    - *Alternative considered*: hand-roll the missing `role`/`aria-modal`/Escape handling directly in the two MCP files, matching `cli-conflict-dialog.tsx`'s approach — rejected, since it would mean writing (and maintaining) a third, still-incomplete variant of logic `ApplicationDialog` already owns correctly.

13. **Agent Configurations OnePiece tab parity**: drop `OnePieceConfigurationPanel`'s outer `SectionPanel` wrapper (and the "OnePiece" title + description it rendered, which only duplicated the already-selected tab's own label) in favor of the same flat `<div className="space-y-4">` structure `AgentGlobalConfigPanel` uses, and add a local search input reusing `CliConfigToolbar`'s exact layout and the existing `agentConfigurations.toolbar.search` string (already generic — "Search saved profiles" — so no new translation keys were needed). The now-orphaned `onepiece.description` key was removed from all 5 locales since nothing else referenced it.
    - *Alternative considered*: keep `SectionPanel` but switch it to the `"plain"` variant added in decision 8 — rejected as a partial fix; it would remove the border but leave the redundant title/description, the missing search input, and the button-before-status ordering difference from sibling tabs all unaddressed. Full structural alignment with `AgentGlobalConfigPanel` was the same amount of code and fixed all four aspects of the gap at once.
    - *Alternative considered*: keep the "OnePiece 是 VaneHub 内置的原生 Agent..." explainer copy somewhere (e.g. a tab tooltip) since OnePiece, unlike the three well-known external CLIs, may be unfamiliar to new users — rejected for this change; none of the four tabs currently have tooltips, and adding one only for OnePiece would itself be a new inconsistency. Left as a possible future enhancement, not blocking this parity fix.

14. **Skill Management page fixes**: two independent fixes bundled under one task group since both surfaced from the same page review.
    - *Container treatment*: switch `LifecycleSkillRows`'s wrapper from `border border-border bg-background` to `.ucd-panel`, matching `SkillSelectionPanel` and the empty state in the same file. Low-risk — confirmed via `git log -p` this was an unintentional drift within a single refactor commit, not a deliberate choice, so no user confirmation needed (unlike the search box below).
    - *Local search input*: restore it, reusing the pre-existing `skills.filters.search`/`skills.filters.searchPlaceholder` keys and the already-wired `filters.query` state. This one **required pausing mid-review**: `git log -p` showed the box was deliberately removed in commit `14b67ca` as part of a real, described refactor (not a bug), and a pre-existing test explicitly asserted its absence (`skills-page.test.tsx`: `expect(html).not.toContain("搜索 Skill")`; `tests/e2e/skills-settings.spec.ts`: `not.toHaveCount(0)` on its placeholder). Finding a deliberate-looking prior removal is a different situation from finding an inconsistency — silently reversing the user's own past choice would be wrong even if it looks inconsistent with sibling pages today, so the user was asked directly (with the git history laid out) before writing any code. They confirmed restoring it, at which point the fix became the same low-risk pattern already used for Agent Configurations/MCP/CLI Management: reuse existing translation keys, wire an existing-but-unbound state field, update the tests that had locked in the old behavior.
    - *Alternative considered (search input)*: leave the local box removed and treat the git-history finding as informational only — this was the default/safe choice pending the user's answer; not taken once they confirmed they wanted it back.

15. **Prompt Hook dialog accessibility**: migrate both hand-rolled overlays to `ApplicationDialog`, same target component and same evidence method (scripted `role=dialog` + Escape probe) as MCP dialog accessibility (decision 12). Two overlays — the preview dialog and the lifecycle panel — had no cancel-style button of their own in their body content (they relied entirely on the hand-rolled header's "关闭" button, which `ApplicationDialog` doesn't provide a built-in equivalent for), so an explicit "关闭" button was added to each, matching the same gap-filling approach already used for MCP's import/export dialog (decision 12).
    - *Alternative considered*: autofocus the "ID" field in the create/edit form, matching its position as the first field — rejected, because that field is `disabled` in edit mode and a disabled element can't receive focus, which would leave focus landing nowhere useful half the time. "名称"/name is editable in both modes, so it was chosen instead.
    - *Alternative considered*: also convert the per-Agent CLI-binding checkbox chips (`prompt-hook-card-list.tsx`) to unframed rows, since each one is a `rounded-md border` box nested inside the card's own `.ucd-panel` — rejected after visual review; these are interactive multi-select checkbox targets (not passive display rows), and a distinct bordered "chip" boundary per option is a defensible, common pattern for that interaction shape rather than the decorative redundancy the nested-card rule targets. Documented as investigated-and-left-unchanged rather than silently skipped.

16. **Prompt Hook filter toolbar layout**: bump the toolbar's grid breakpoint from `lg` to `xl` so it matches `PromptHookCardList`'s own 1→2 column breakpoint, and move the result-count summary to sit directly under the filters instead of after the whole card list.
    - *Alternative considered*: add an intermediate breakpoint (e.g. 3-column at `md`, 5-column at `xl`) instead of a single jump from stacked to 5-column — rejected as unnecessary complexity; the stacked (single-column) layout already reads cleanly at every width below `xl` in the screenshots, so there's no dead zone that needs a third state.
    - *Alternative considered*: give the result-count summary its own dedicated prop on `PromptHookFilterToolbar`, matching `SkillFilterToolbar`'s `resultCount` prop, instead of leaving it as a separately-rendered sibling `<div>` in the page — rejected for this round as a larger API change than the fix needed; simply reordering the existing JSX in `prompt-hooks-page.tsx` achieves the same visible outcome with a much smaller diff.

17. **SSH Connections page fixes**: three fixes bundled since all three surfaced from the same page review. Migrate the dialog to `ApplicationDialog` (same pattern as decisions 12 and 15). Replace the broken `ucd-status-info` badge with the shared `Badge` component and an explicit `testStatus → tone` map (`not-tested`/muted, `succeeded`/success, `failed`/danger) rather than defining a new `ucd-status-info` CSS class — the app already has a complete muted/success/warning/danger tone vocabulary via `Badge`, and this status has exactly three states that map cleanly onto three of the four existing tones, so adding a distinct "info" tone system-wide would be unused scope beyond this one badge. Defer validation-error display until the first submit attempt (a `submitted` flag), matching the `inline-validation`/`error-clarity` guidance already applied elsewhere in this app — the underlying validation logic (and the derived `invalid` boolean used to gate the eventual save) is unchanged, only when the error text renders changed.
    - *Alternative considered*: keep the Save button disabled until the form is valid (the original behavior) rather than enabling it and gating only the error display — rejected; with premature errors now hidden, an always-disabled Save button on a blank form would look inert with no explanation of why, whereas an enabled button that reveals errors on click gives the user a clear, standard way to discover what's required.

18. **Extensions page fixes**: three fixes, one of which (the `StatusPill` root cause) necessarily reaches beyond the page the user named this round.
    - *Dialog*: migrate to `ApplicationDialog`, same as decisions 12/15/17. No autofocus target set inside it deliberately — this is a review/confirm dialog for a consequential (download+install) action, not a form, so it follows the same "no autofocus on the consequential action" precedent already used for this change's delete-confirmation dialogs rather than the "autofocus the confirm button" precedent from the pre-existing `CliConfigActionDialog`; the dialog container itself receives focus via `ApplicationDialog`'s built-in fallback.
    - *Nested card*: `variant="plain"` on the wrapping `SectionPanel`, reusing decision 8's fix. Side effect noted and accepted: `variant="plain"`'s `last:border-b-0 last:pb-0` styling (designed for multiple stacked plain sections inside a disclosure) strips this standalone section's own bottom divider line, since it's `SectionPanel`'s only instance on the page and therefore matches `:last-child`. Spacing is unaffected (the header's own `mb-4` is unconditional), only the divider line disappears — judged a minor, acceptable cosmetic side effect of reusing existing infrastructure rather than inventing a one-off header style for a single call site.
    - *StatusPill*: change to a required explicit `tone` prop (matching `Badge`'s existing convention) instead of sniffing translated text. Making it required rather than optional-with-a-fallback was deliberate — an optional prop defaulting to the old text-sniffing behavior would leave the exact same landmine in place for any future caller.
    - *Alternative considered (StatusPill)*: leave `StatusPill` untouched and have `extensions-page.tsx` render its status pill via `Badge` directly instead, sidestepping the broken shared component without touching `sdk-page.tsx` — rejected. This is a confirmed bug (not a prior deliberate design decision, unlike decision 14's search box), so unlike that case there was no ambiguity to preserve by staying narrow; leaving a known-broken shared component in place, still silently miscoloring `sdk-page.tsx`'s error/update-available states, would mean choosing to ship a known bug over a same-sized fix.

19. **Plugin Integrations nested card**: same `variant="plain"` fix as decision 18, reused for a second page with the identical shape. No dialog or `StatusPill` work needed here — this page already does both of those things correctly, so the fix is a single one-line variant change.

20. **Execution Observability nested card**: same `variant="plain"` fix, applied only to "MCP 观测能力" — the other three `SectionPanel`s on this page keep their default "card" variant since their single-static-box shape doesn't need it (see context note above). Also added the missing `icon={Boxes}` while touching this section, reusing the icon already associated with the "MCP 服务器" concept elsewhere in the app's own settings navigation.
    - *Alternative considered*: fix the nested card without adding the icon, to avoid the resulting size/tint mismatch between this section's now-`variant="plain"` icon avatar and its three `variant="card"` siblings on the same page — rejected after checking: `variant="plain"` + `icon` is already an established combination (used by 4 sections in Basic Settings' advanced-config disclosure), so the smaller/differently-tinted icon avatar is `variant="plain"`'s existing, already-shipped look elsewhere in the app, not a new visual language being introduced here. The alternative would have left a real, visible gap (this section is the only one of four on the page with no icon at all) to sidestep a much subtler and already-precedented styling difference.
    - *Alternative considered*: keep "MCP 观测能力" as `variant="card"` (matching its three siblings exactly, no icon-size question at all) and instead strip the border from the four inner capability chips, replacing it with a background-tint-only treatment — rejected in favor of consistency with how every other nested-card fix in this change (task groups 8, 18, 19) was done: change the outer wrapper, not the inner repeated items, since the inner items are the actual content being listed and should keep their own card identity.

21. **Usage Statistics page fixes**: same `variant="plain"` fix applied twice (trend chart section, agent breakdown section), plus one unrelated grid-alignment fix (`items-start`) found while reviewing the same page.
    - *Distinguishing "repeated" from "fixed-pair" nesting*: `usage-trend.tsx`'s two `TrendLine`s and `usage-accounting-note.tsx`'s note+timestamp pair both nest exactly 2 boxes inside a `SectionPanel` — superficially similar counts, but judged differently. `TrendLine`'s two boxes are the *same* shape/size (label + total + sparkline, side by side in an even `sm:grid-cols-2`), reading as two instances of one repeatable "chart card" concept — the shape the anti-pattern rule targets. `usage-accounting-note.tsx`'s two boxes are *different* shapes/sizes/purposes in an asymmetric `minmax(0,1fr)_auto` grid — a note next to a timestamp, not two instances of the same thing. The rule cares about visual repetition of a card-shaped unit, not the literal count of nested `<div>`s.
    - *Alternative considered*: leave the two-column grid's `stretch` behavior alone since it's arguably intentional (equal-height columns can look more organized than jagged bottom edges) — rejected once the actual data state was screenshotted: with only 1–2 agents, the stretch produces a large, clearly-empty gap rather than a subtle alignment nicety, and `items-start` costs nothing when the columns happen to be similar heights (many agents) since content naturally fills the space either way.

## Risks / Trade-offs

- [Risk] Applying shared panel/card classes to Loop Center may shift spacing enough to break the existing `tests/e2e/loop-engineering.visual.spec.ts` baseline → Mitigation: intentionally review and update that visual baseline as part of this change instead of accepting the diff blindly.
- [Risk] Toast timer ownership changes could interact with the existing bounded-history/eviction behavior → Mitigation: only touch timer lifecycle ownership; leave the bounded-list/eviction logic untouched.
- [Risk] Collapsing top bar search to an icon at ≤900px changes a control some users may already rely on at that width → Mitigation: trigger the change only at the already-established 900px breakpoint so responsive behavior stays internally consistent with the activity bar/sidebar, which already change at the same width.
- [Risk] Removing the extra English line from the Agent Terminal mock notice could look like reduced diagnostic detail → Mitigation: the string is still locale-selected (zh-CN or en); English-locale users still see one clear English line, just not both languages at once.
- [Risk] Removing per-field borders in the info panel could reduce scannability if rows aren't visually separated some other way → Mitigation: use row dividers or consistent spacing (already an established pattern via `SettingsRow`'s `border-b` divider) instead of removing separation entirely.
- [Risk] Moving "批量管理"/"归档" into an overflow control could reduce discoverability of batch delete for existing users → Mitigation: keep both actions one interaction away (single overflow open), not buried further; this mirrors how Settings' own list pages already use overflow patterns for secondary actions.
- [Risk] Adding a `"plain"` `SectionPanel` variant could get reused in inappropriate contexts later (e.g. a top-level page section that should stay a full card) → Mitigation: keep the variant's name and this design's rationale (only for sub-topics already inside a disclosure) as the guardrail; the four current call sites are all disclosure-nested today.
- [Risk] Migrating `FolderOpenersSection` to `SettingsDisclosure` could change its exact spacing/typography enough to look different from before → Mitigation: this is the intended outcome (align it to the shared pattern); verify visually in both styles before considering it done.
- [Risk] Removing OnePiece's explainer title/description could leave new users without context on what "OnePiece" is → Mitigation: the tab's icon + label plus the panel's own "配置状态"/"API 提供商" headings still communicate the page's purpose; this matches how the other three tabs (also non-obvious to a first-time user) already rely on the same level of in-panel context without a dedicated explainer.
- [Risk] Restoring Skill Management's local search input reverses a real, described prior refactor (commit `14b67ca`) rather than fixing an obvious bug → Mitigation: not treated as a routine fix — the git history was surfaced to the user and restoration only proceeded after explicit confirmation.
- [Risk] Removing the Prompt Hook overlays' hand-rolled header close button and relying on newly-added footer/body close buttons could be missed by users used to the old top-right placement → Mitigation: the new buttons reuse the same "关闭" label and remain visually prominent (top of body for the lifecycle panel, end of footer for preview); backdrop-click and Escape now also work as additional, previously-broken affordances.
