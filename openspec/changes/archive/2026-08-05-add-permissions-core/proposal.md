## Why

Native API agents already have a coarse approval mechanism (archived `agent-tool-trust` + `agent-tool-execution`): a pure two-value risk classifier (`risk_tier_for`), a single-call `resolve_tool_approval` command, and a per-agent global boolean (`agents.auto_approve_tools`) that only ever covers `shell`/`file`-write, with MCP calls unconditionally gated and Plan Mode unconditionally overriding. CLI agents (Claude Code, Gemini CLI, OpenCode, Codex CLI) have no equivalent at all — they launch through a native PTY wrapper (`agent-terminal-runtime`) and their own approval prompts render directly inside that terminal, completely invisible to VaneHub: no shared audit trail, no shared policy, no way to reason about "what is this agent allowed to do" across agent kinds. `multi-agent-coordination` and `loop-engineering-runtime` are already live capabilities, and `loop-engineering-runtime` today gates API-agent Worker/Verifier roles behind the blunt `auto_approve_tools` flag as a stand-in for real permission scoping. Without a CLI-agnostic decision core, every future execution surface (each CLI's own PEP, PTY fallback, multi-agent delegation) would reinvent approval logic independently, and native-agent vs. CLI-agent approval would remain two mutually invisible audit blind spots. This change establishes that decision core — a Policy Decision Point (PDP) — and migrates the native agent onto it first, so there is exactly one approval/audit path from day one instead of two that later need reconciling.

This is Phase 1 of a five-phase roadmap (see `design.md` Roadmap appendix): `add-permissions-core` (this change) → `add-claude-code-permission-callback` → `add-policy-compiler` (Codex/Gemini/OpenCode) → `add-pty-interception` → `add-agent-delegation-budget`. Each later phase starts only once its predecessor is archived.

## What Changes

- Affects the **desktop runtime only** for real enforcement (native API agents and their tool-use loop don't exist in the Web/mock runtime's real sense); the Web/mock runtime gains deterministic simulation parity for the new service contracts, matching the pattern `agent-tool-trust`/`agent-tool-execution`/`agent-mcp-tools` already established.
- Add a new bounded context `src-tauri/src/contexts/permissions/` (domain/application-ports/infrastructure/api.rs, per this project's actual DDD layout) owning a Policy Decision Point: domain model `Principal` (identified by a stable agent id — one durable principal per agent, persisting across every session that agent participates in, matching the legacy trust flag's own cross-session scope; `parent_principal_id`/`budget_config` columns reserved but rejected when set — `delegation_not_enabled` — until a later phase activates them; session id and generation id travel as per-call evaluation context, not as part of the principal's identity), `Action` (open `String` newtype with known constants `shell.exec`/`file.read`/`file.write`/`mcp.tool`/`memory.write`, not a closed enum, so future CLI-specific concepts don't force a breaking taxonomy change), `Effect` (`Allow`/`Deny`/`Ask`, replacing today's two-value `ToolRiskTier`), `RiskLevel` (`L0`-`L3`; Phase 1 only produces `L0`-`L2`), `Scope` (`Once`/`Session`/`Project`/`Global` — a capability that does not exist today), and `Policy` (principal/action/resource matchers → `Effect`, priority-ordered, explicit Deny > explicit Allow > default Ask).
- Add four policy templates — `readonly`/`standard`/`trusted`/`yolo` — where `trusted` is defined to be behaviorally equivalent to today's `auto_approve_tools = true` (this equivalence is a migration acceptance criterion, not just a description).
- Two invariants stay outside the policy table entirely and no policy or template (including `yolo`) can override either: MCP-sourced tool calls are floored at `Ask` as an `evaluate()` precondition (preserves `agent-mcp-tools`'s existing "no automatic approval path" guarantee), and Plan Mode's existing unconditional tool restriction — already enforced independently at the tool-catalog and dispatch layer, before and regardless of any approval decision — is left untouched rather than duplicated inside `evaluate()` (preserves `agent-chat-configuration`'s existing guarantee without creating a second place that could drift out of sync with it).
- Add three SQLite tables via an additive migration continuing the existing versioned sequence: `agent_principals` (principal identity, its currently assigned policy template, and the reserved delegation/budget columns — a template's rules are a pure function of its name, so no separate table is needed to store what a template assignment expands to), `permission_grants` (remembered decisions; only `Scope=Session/Project/Global` grants persist here, `Once` does not), `approval_audit` (includes a `channel` column; Phase 1 only ever writes `native_agent`, reserving `mcp_callback`/`policy_static`/`pty_interception` for later phases).
- One-time data migration: for every existing agent row, `auto_approve_tools = true` becomes a `trusted`-template policy assignment, otherwise `standard`; application code stops reading/writing `agents.auto_approve_tools` after migration (whether the column itself is physically dropped is left to `tasks.md`).
- Rewire the native agent's tool-use round trip: the approval-gate call site switches from `risk_tier_for(...) == RequiresApproval` to `permissions::api::evaluate(principal, action, resource) -> Effect`, branching on all three effects — `Allow` executes immediately (as `AutoApprove` does today), `Deny` skips execution and reports the denial back to the provider (reusing the existing "denial reported to provider, generation continues" path from `agent-tool-execution`, now reachable from a policy decision and not only a human's), `Ask` suspends the call pending human input (as `RequiresApproval` does today). `risk_tier_for` itself is unchanged and keeps its existing unit tests; it no longer is the final approval authority.
- Add an `ApprovalBroker`: the Rust side owns the pending-approval queue as the single source of truth, pushes a `permission://request` Tauri event, and the frontend additionally pulls the full pending list on mount to compensate for events missed while minimized or reloading. Pending-approval visibility reuses the existing `notification-system` capability rather than introducing a new badge mechanism.
- **BREAKING**: Remove the `resolve_tool_approval` and `set_agent_tool_trust` Tauri commands and their frontend methods; no compatibility shim is kept. Replace with new commands under `permissions` (resolve a pending approval; apply a policy template to an agent's principal). The Agent settings UI's binary trust toggle becomes a policy-template picker; a new approval-card UI shows the principal chain, action, resource, risk level, and a Once/Session/Project/Global "remember this" scope picker. (`file.write`'s diff-preview presentation is deliberately left to implementation time, not designed here.)
- All new user-visible strings ship through i18n resources for every registered locale and follow the existing `futuristic`/`minimal` semantic-token, 8px-radius, no-card-in-card visual rules — these are pre-existing project-wide requirements, not new ones introduced by this change.
- Extend the required architecture test to verify `permissions::domain` has no Tauri/Rusqlite/filesystem/process dependency and that `agent_runtime` only reaches `permissions` through its `api` facade. Add a migration-equivalence regression test asserting that an agent with pre-migration `auto_approve_tools = true` still resolves `shell.exec`/`file.write` to `Allow`, `mcp.tool` to `Ask`, and Plan Mode still hard-rejects, after migration.

## Capabilities

### New Capabilities
- `permissions-core`: The PDP domain model (Principal/Action/Resource/Effect/Scope/RiskLevel/Policy), the SQLite-backed policy store and evaluation engine, policy templates, and the migration from `agent-tool-trust`.
- `permissions-approval`: The pending-approval queue (`ApprovalBroker`), its Tauri event/pull-reconciliation contract, the approval-card and policy-template-picker UI, and Web/mock parity.

### Modified Capabilities
- `agent-tool-trust`: Superseded by `permissions-core`. The persistent per-agent trust setting, its dedicated confirmation UX, and its MCP/Plan-Mode exclusions are replaced by policy templates and the two `evaluate()` invariants, with `trusted`-template equivalence as the migration contract.
- `agent-tool-execution`: The "risk-tiered tool approval" and "approval request and resolution" requirements' decision point changes from `risk_tier_for`'s direct two-value output to `permissions::api::evaluate()`'s three-value output; sandboxed execution, tool-use-loop mechanics, and message persistence are unaffected.

## Impact

- Affected code (desktop runtime): new `src-tauri/src/contexts/permissions/{domain,application,infrastructure,api.rs}`, new `src-tauri/src/commands/permissions/`, `agent_runtime`'s tool-use round trip (`infrastructure/api_process_adapter.rs` approval-gate call site), `platform::database` migrations (+1 version), removal of `resolve_tool_approval`/`set_agent_tool_trust` commands.
- Affected code (frontend): new `src/services/permissions.ts` + `runtime-permissions-client.ts` + `tauri-permissions-client.ts` + `web-permissions-client.ts`; Agent settings UI trust toggle replaced by a policy-template picker; new approval-card UI component.
- Affected specs: adds `permissions-core`, `permissions-approval`; modifies `agent-tool-trust`, `agent-tool-execution`.
- Out of scope (deferred to later, already-agreed phases): per-CLI PEP adapters for Claude Code (Phase 2), Codex/Gemini/OpenCode (Phase 3); PTY-based approval interception (Phase 4); delegation-chain intersection and budget/circuit-breaker enforcement (Phase 5 — this change only reserves the `parent_principal_id`/`budget_config` columns and rejects any attempt to use them).
- Dependencies: none (first change in the roadmap).
