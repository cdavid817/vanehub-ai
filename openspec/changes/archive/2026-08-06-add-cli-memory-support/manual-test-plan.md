## 前置准备

1. **构建并启动桌面应用**（不是 Web/mock 预览——本次验证的核心行为依赖真实 Tauri 后端 + 真实 CLI 子进程 + 真实 OnePiece 网络调用，Web/mock 模式无法验证这些）。
2. **配置 OnePiece 凭据**：设置齿轮图标 → 左侧导航「Agent 配置」（Agent Configurations）→ 页内 Tab 切到「OnePiece」→ 点击「新增配置」/「编辑配置」，填入 provider、接口格式、模型 ID、API Key → 保存后点击「启用」，状态徽章应显示「已就绪」。
3. **确认至少一个 CLI Agent 可用**：设置 → 「CLI 管理」（CLI Management）确认对应 CLI（建议用 Codex CLI 或 Claude Code）已检测到可执行文件；如需自定义启动参数，在「Agent 配置」对应 Tab 或「CLI 参数」页设置。
4. **打开「个性化」设置页**：设置 → 左侧导航「个性化」（Personalization）。页面从上到下依次是「自定义指令」区块、「记忆」区块——本次测试主要操作「记忆」区块。确认「启用记忆」开关是打开状态（默认应为开）。

## 场景 1：跨 Agent 记忆共享可见

**目标**：验证 spec.md "Memory scoping" 要求——任一 agent（OnePiece 或某个 CLI）产生的记忆，在其它 agent 的会话和管理面板里都可见，不再按 agent 隔离。

**操作步骤**：

1. 新建一个 **CLI Agent**（如 Codex CLI）的会话（会话侧边栏「新建」→ 选择该 Agent → 选工作区 → 创建），在会话里发一条有具体信息量的消息，例如：
   > "记住：这个项目用 pnpm 管理依赖，端口固定用 5199。"
2. 等待这一轮 CLI 回复完成（消息状态变为已完成）。
3. 打开设置 → 「个性化」→ 「记忆」区块，观察「已保存的记忆」列表。
4. 记录列表中是否出现一条新记忆，其来源徽章（agentId）是否显示为该 CLI 的 id（如 `codex-cli`）。
5. 回到会话侧边栏，新建一个 **OnePiece** 会话（或已有的 OnePiece 会话），随便发一条消息。
6. 再次打开「个性化」→「记忆」区块，确认第 4 步那条记忆**仍然可见**，且列表里能同时看到 `codex-cli`（或你实际用的 CLI）和 `onepiece` 两种来源徽章共存于同一个列表。
7.（可选，更强验证）在 OnePiece 会话里问一个只有依赖第 1 步记忆内容才能正确回答的问题（例如"这个项目用什么包管理器？"），确认 OnePiece 的回答体现出它"知道"CLI 会话里存的信息。

**预期结果**：
- 记忆列表不按 agent 分开显示，是同一个池子。
- 列表每一项都带来源 agent 的徽章，能看到不同 agent 产生的记忆混在一起。
- 第 7 步（如做）：OnePiece 的回答体现出跨 agent 记忆确实被注入进了它的 system prompt。

## 场景 2：CLI 对话结束后产生新记忆（已配置 OnePiece 凭据）

**目标**：验证"CLI 生成完成后独立触发一次抽取调用"这条新机制真的在跑，而不只是场景 1 里"看起来正常"的巧合。

**操作步骤**：

1. 确认 OnePiece 凭据已配置且状态为「已就绪」（同前置准备第 2 步）。
2. 打开「个性化」→「记忆」区块，先点「重置全部」清空现有记忆（弹出确认对话框后确认），把列表清零，方便本场景观察增量。
3. 新建一个 CLI Agent 会话，发一条包含明确事实的消息并等待其回复完成。
4. 打开该会话的「日志」（Logs）Tab，在「搜索脱敏日志」框里输入 `memory-extraction`，确认能看到一条 `session.runtime.memory-extraction` 相关的日志（本场景走的是成功路径，正常情况下这条日志出现意味着走过了抽取逻辑；具体是否记录成功态日志、还是仅在失败时记录 Warn，以实际日志内容为准，记录下来）。
5. 回到「个性化」→「记忆」区块，刷新页面（或切出再切回该设置页触发重新查询），确认列表中新增了一条 `source` 标签为「自动提取」的记忆，来源 agentId 是该 CLI。

**预期结果**：
- 每一轮 CLI 对话结束后都应该产生新记忆（当前是 MVP："每轮都抽"，没有节流），不需要像 OnePiece 那样对话长度攒到阈值才触发。
- 新记忆的 `source` 是「自动提取」（对应 `automatic`），不是「主动要求记住」（`explicit`）。

## 场景 3：未配置 OnePiece 凭据时优雅降级

**目标**：验证 CLI 记忆抽取在 OnePiece 不可用时安全跳过，且不影响 CLI 消息本身的正常收发。

**操作步骤**：

1. 打开设置 → 「Agent 配置」→「OnePiece」Tab，把当前生效的 OnePiece 配置**禁用**或删除 API Key，使状态变回「待配置」（测试完成后记得恢复，避免影响后续其它测试）。
2. 新建一个 CLI Agent 会话（或复用已有会话），发一条消息。
3. 观察：
   - CLI 的回复是否**正常完成**，内容、耗时跟 OnePiece 已配置时相比没有明显异常（不应该被卡住、报错或明显变慢）。
   - 打开该会话「日志」Tab，搜索 `memory-extraction`，应该能看到一条 Warn 级别日志，措辞类似"OnePiece 没有可用凭据，跳过"（对应代码里 `AgentRuntimeApplicationError::Credential` 分支）。
   - 打开「个性化」→「记忆」区块，确认**没有**新增任何来源为这个 CLI、`source` 为「自动提取」的记忆。
4. 测试完成后，恢复第 1 步的 OnePiece 配置（重新填入 API Key 并启用），以免影响之后的使用。

**预期结果**：
- CLI 消息发送/接收完全不受影响。
- 有一条清晰的 Warn 日志说明"跳过了"，而不是静默失败或抛出用户可见的错误。
- 记忆列表没有增加任何新条目。

## 场景 4：重置确认文案清楚说明影响范围

**目标**：验证"重置全部"操作的二次确认文案，能让用户明白这会清空**所有 agent** 共享的记忆，而不只是当前正在看的这个 agent。

**操作步骤**：

1. 确保「记忆」列表里至少有几条记忆，且能看到不止一种来源 agentId（可以先重复场景 1 的步骤攒几条）。
2. 点击「重置全部」按钮。
3. 仔细阅读弹出的确认对话框文案。中文版预期文案为：
   > 删除所有已保存的记忆（OnePiece 和全部 CLI Agent 共享）？此操作不可撤销。
4. 确认该文案是否清楚传达了「这会删掉所有 agent 的记忆，不只是某一个」这个信息，判断是否需要进一步改进措辞（如果观感上仍然容易被误解成"只清空当前列表里选中的"或"只清 OnePiece 的"，请在备注里写明具体哪里读起来会有歧义）。
5. 点击确认，验证记忆列表清空（包括之前不同 agent 来源的那些记忆一起消失，不是只删了部分）。

**预期结果**：
- 确认文案明确提到"OnePiece 和全部 CLI Agent 共享"或等价表述。
- 确认后列表清空，之前看到的所有来源 agent 的记忆全部消失，没有遗漏。
