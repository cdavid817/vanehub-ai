## Why

VaneHub can register user-defined API agents, but it does not yet expose its own stable native Agent identity, and the create-session flow currently only admits a fixed list of CLI agents. OnePiece should become VaneHub's first-party native Agent: always discoverable, explicitly configured by the user, and backed by the existing API runtime, tools, Skills, memory, and approval model rather than a parallel execution stack.

## What Changes

- Add a built-in Agent with the stable id `onepiece`, API interaction mode, first-party visual identity, versioned core instructions, and capability metadata. OnePiece reuses the existing direct-provider API runtime and does not introduce another launch kind.
- Add a OnePiece setup lifecycle that keeps the Agent visible before provider configuration, reports why it is not ready, and supports multiple named upstream-provider Profiles with independently secured credentials.
- Let users choose from a built-in provider directory shared by the OnePiece, Claude Code, Codex CLI, and OpenCode configuration tabs, then add, edit, delete, and explicitly activate named Profiles through the owning Agent's existing lifecycle. The directory contains 25 stable vendor identities and one or more reviewed endpoint configurations per vendor, keyed by wire protocol such as Anthropic Messages, OpenAI Chat Completions, or OpenAI Responses. Provider identity, endpoint protocol, interface format, and Base URL are resolved from the selected directory entry rather than entered manually.
- Source the multi-endpoint matrix from reviewed CC Switch and Cherry Studio provider-registry definitions. Preserve distinct OpenAI and Anthropic endpoints when a vendor publishes both, represent an unavailable protocol explicitly instead of fabricating a URL by suffix, give every vendor a bundled Cherry Studio provider mark with recorded MIT provenance and trademark attribution, and keep unsupported OAuth/CLI-only, local, or user-entered hosts out of the fixed directory.
- Let each Agent configuration adapter consume the same vendor identities, endpoint metadata, catalog search/filter components, cards, and icon component while translating only compatible endpoint records into that Agent's existing Profile payload. OnePiece and OpenCode may select either supported protocol; Claude Code prefers a published Anthropic endpoint; Codex CLI prefers Responses and then Chat Completions. An endpoint that requires protocol translation SHALL remain unavailable until VaneHub owns an explicit conversion layer.
- Discover compatible models through catalog-owned provider endpoints after the user supplies a credential, merge the live response with a small bundled fallback list, and replace free-text model entry with a searchable selection while preserving legacy saved values.
- Add a shared, explicit API-credential verification action to the Claude Code, Codex CLI, OpenCode, and OnePiece configuration surfaces. The action validates either the transient credential currently being edited or a saved Profile credential by issuing a bounded minimal request through the Profile's effective Anthropic Messages, OpenAI Chat Completions, or OpenAI Responses endpoint; it distinguishes authentication rejection from model/endpoint rejection and transient provider failure without persisting validation state or exposing secrets.
- Present OnePiece provider setup with the same visual hierarchy as CLI configuration: an “Add configuration” toolbar action, searchable built-in provider catalog, readiness/status feedback, multiple provider cards, explicit active state, and application-owned add/edit/delete/activate dialogs instead of a permanently expanded inline form or custom endpoint editor.
- Derive API-Agent availability from the complete provider configuration and actual credential presence without contacting the provider; an unconfigured OnePiece remains visible but cannot be selected for session creation.
- Assemble OnePiece's provider-native system prompt deterministically from its non-removable core instructions, optional bound Skills, and scoped memories. Core instructions remain outside compacted conversation turns and cannot disappear because a Skill is disabled or unavailable.
- Replace the create-session dialog's fixed four-Agent allowlist with service-backed eligibility based on registered Agent capabilities and supported interaction modes. Show OnePiece prominently, use `interactionMode = api` when it is selected, and present an actionable configuration state when it is not ready.
- Make the native session-creation boundary accept a declared `api` interaction mode and validate the selected Agent's supported mode and readiness instead of maintaining a separate CLI-oriented string allowlist.
- Prevent deletion of the built-in OnePiece identity while allowing its provider configuration and credential to be reset or replaced. Existing user-registered API agents retain their current lifecycle rules.
- Preserve desktop/Web parity through the shared frontend service boundary: the Tauri adapter uses native commands and secure credentials, while the Web adapter exposes deterministic OnePiece configuration, selection, session creation, and prompt-influence behavior without real provider calls.
- Keep existing CLI agents and user-registered API agents behaviorally compatible; this change is additive and introduces no new runtime dependency.

## Capabilities

### New Capabilities

- `onepiece-native-agent`: Defines OnePiece's stable built-in identity, configuration/readiness lifecycle, core instructions, visual presentation, safe defaults, and desktop/Web behavior on top of the existing API-Agent runtime.

### Modified Capabilities

- `api-agent-runtime`: Adds multiple provider Profiles, active-Profile resolution, and credential-aware readiness behavior for a pre-registered built-in API Agent while preserving normal user-created API-Agent registration and generation.
- `agent-lifecycle-management`: Allows OnePiece provider Profiles to be added, edited, activated, deleted, or removed together, and prevents deletion of the built-in identity, without changing ordinary API-Agent edit/delete semantics.
- `session-management`: Discovers eligible session Agents from service-backed registry data, permits declared API interaction modes at the native boundary, and lets users create a session for a ready OnePiece using its stable id.
- `agent-skill-injection`: Treats bound Skills as one optional section of a larger system prompt, preserving OnePiece core instructions when no Skill is bound or Skill resolution fails and defining deterministic prompt-section ordering.

## Impact

- **Desktop runtime:** additive SQLite migration/seed data for the stable OnePiece identity and multiple catalog-backed provider Profiles; a versioned shared 25-vendor/multi-endpoint directory with provider icon and endpoint-scoped model-discovery metadata; persisted OnePiece endpoint selection; per-Profile secure credentials; safe credential-aware model listing; active-Profile projection into the API runtime; credential-aware availability; Agent runtime prompt composition; session-creation validation; Tauri commands and DTO mapping where new configuration operations are required.
- **Web runtime:** matching in-memory OnePiece identity, multiple provider Profiles, active-Profile switching, readiness transitions, deterministic catalog-backed model discovery, session selection, and deterministic mock generation signals.
- **Frontend:** `AgentService`, Tauri/Web clients, Agent types/contracts, Cherry Studio-derived provider marks with third-party notices, shared provider-directory/search/card/endpoint components across the four Agent configuration tabs, catalog-backed OnePiece settings/setup UI with no manual provider or Base URL fields, create-session Agent discovery and grouping, readiness feedback, localization, and visual identity.
- **Architecture:** React remains dependent only on the service boundary; credential access, persistence, availability, and provider execution remain native/runtime adapter responsibilities. Existing `launch_kind = api` routing is reused.
- **Verification:** focused Rust and frontend tests, contract-conformance coverage, Web/mock parity tests, API-credential verification coverage across all four Agent configuration tabs, Playwright session-creation coverage, full project validation commands, and manual desktop smoke tests with a real DeepSeek credential over its reviewed Anthropic Messages-compatible and OpenAI-compatible endpoints.
