## Context

Phase 1 (`add-permissions-core`) built the whole decision engine: `EvaluationService::evaluate(principal, action, resource, ...) -> Effect` (`Allow`/`Deny`/`Ask`), four policy templates, SQLite-backed principals/grants/audit trail, and `ApprovalBroker` for the `Ask` case (pending-approval queue, `permission:request` event, `ApprovalCard` UI, a 300-second fail-closed timeout — `APPROVAL_TIMEOUT_SECONDS`, `src-tauri/src/bootstrap/permissions.rs:18`). All of it is wired to exactly one caller today: the native API agent's tool-use loop, through `AgentPermissionPort`/`PermissionsPortAdapter`.

Claude Code CLI runs in a genuine interactive PTY (`agent-terminal-runtime`'s "Interactive CLI profile injection" requirement), never `-p`/headless mode. That rules out `--permission-prompt-tool`, which this session confirmed (via official `code.claude.com/docs`) is non-interactive-mode-only. `PreToolUse` hooks, by contrast, are confirmed to be a real synchronous decision gate in interactive mode: a documented stdin/stdout JSON contract, registered via `.claude/settings.json`, evaluated per tool call. Two mechanics matter for this design: hooks default to a 600-second timeout, and (for the `"type": "command"` variant, the only one confirmed usable for `PreToolUse` — see Non-Goals) each invocation spawns a fresh process rather than reusing a long-lived connection.

Separately, `cli_config` already owns a proven pipeline for Claude Code's `settings.json`: atomic merge-write, preserving unrelated top-level fields including `hooks` (`cli-agent-config-management`'s "Claude Code global projection" requirement), fingerprint-drift detection, and rollback on partial failure. `src-tauri` has no existing local network listener of any kind (`axum`/`warp`/`hyper::Server`/etc. — none present).

## Goals / Non-Goals

**Goals:**
- Give Claude Code CLI real, enforceable, audited permission control for the tool categories VaneHub's `Action` model already covers, using the same decision pipeline native agents already go through.
- Fail in a way that is safe by default for high-risk actions and non-disruptive for low-risk ones when VaneHub itself is unreachable.
- Reuse Phase 1's PDP and `cli_config`'s settings.json machinery rather than building parallel versions of either.

**Non-Goals:**
- Gemini CLI, OpenCode, Codex CLI. None expose a confirmed equivalent synchronous permission gate; both the inherited roadmap sketch and independent research into a sibling project (clowder-ai) converge on Claude Code being the only one of the four worth this integration today.
- Per-project or per-session Claude Code policy. One global `claude-code` principal, matching how every other principal in the system is already identified by agent id alone (`permissions-core`'s "Unified permission decision model").
- New `Action`/`Resource` variants. Only `shell.exec`, `file.write`, `file.read`, and `mcp.tool` are mapped; tools without a clean mapping are simply not matched by the hook.
- Confirming whether `"type": "http"` hooks fire for `PreToolUse`. It's documented to exist (`{"type": "http", "url": ..., "headers": ..., "allowedEnvVars": ...}`), and — per the fault-injection PoC (`poc-findings.md`) — current docs do show a worked `PreToolUse` + `http` example, which is new information; earlier research in this session had only found `PostToolUse` examples. Documentary evidence is still not the same as confirmed runtime behavior: the PoC's attempt to trigger this empirically was blocked by an environment limitation (a nested Claude Code session cannot independently authenticate a second concurrent `claude` process — `poc-findings.md` Finding D), not by anything about the hook mechanism itself. This design proceeds on `"type": "command"` only, which is empirically confirmed end-to-end. Resolving the `http` question empirically is left to whoever next runs a non-nested `claude` session (`poc-findings.md` has a 5-minute reproduction recipe); it remains non-blocking either way.
- Changing how Claude Code itself launches. Still PTY, still through `agent-terminal-runtime`, unchanged by this phase.

## Decisions

**D1 — Add a PEP, not a second PDP.** The loopback HTTP handler is a thin translation layer: parse the hook payload into `Action`/`Resource`, call the existing `evaluation_service.evaluate()` / `ApprovalBroker.create_pending()`, return the existing `Effect`. This mirrors `agent_runtime`'s own integration exactly (same pattern, new adapter) and means `permissions-core`'s decision logic does not change at all — only its scenario text broadens from "native API agent" to cover this second caller.

**D2 — One global `claude-code` principal.** Not per-project, not per-session. Alternative considered: scope by `project_key` (the field already exists in `ApprovalRequest`/grants). Rejected because it adds a second identity axis nothing else in the system has, and because the installation surface (a single machine-wide `settings.json`) doesn't naturally partition by project anyway — a per-project policy would be enforced by a global hook regardless, which is a false precision.

**D3 — Transport: loopback HTTP (127.0.0.1) + a bearer token generated once per launch.** Considered three options:
  - *Named pipe / Unix domain socket*: filesystem-permission-scoped rather than any-local-process-reachable, but doubles the implementation (separate Windows/Unix APIs) and the hook wrapper can no longer be a trivial HTTP client — rejected, security gain doesn't clear the added complexity given the token already mitigates the loopback-HTTP exposure.
  - *File/DB mailbox with polling*: no new listener at all, but latency is bounded by poll interval — either wasteful high-frequency polling from a process that lives for one tool call, or piggybacking on the existing 30-second sweep (`TIMEOUT_SWEEP_INTERVAL_SECONDS`), unusable for an interactive "may I run this" prompt — rejected.
  - *Loopback HTTP + token (chosen)*: one implementation for all platforms, trivially fault-injectable (kill/hang/delay a process), matches the inherited constraint that the callback needs its own await-timeout semantics. Port is randomized per launch; token is generated once per launch; both are written to a local discovery file the wrapper reads fresh on every invocation (it's a new process each time regardless, so there's no caching concern).

**D4 — Hook wrapper is a new compiled Rust binary, not a shell/PowerShell/Node script.** Ships from the same Cargo workspace and build pipeline as the main app; avoids assuming Node or an unrestricted PowerShell execution policy is available on the target machine. Its job is intentionally minimal: read stdin, read the discovery file, POST with a bounded timeout, translate the response.

**D5 — Offline fallback is risk-tiered, and asymmetric by design.** When the wrapper cannot reach the server at all (not running, connection refused, timeout, discovery file missing), it does not attempt to replicate `risk_level_for()`. It carries a small hardcoded allowlist of tool names known to be read-only (`Read`, `Glob`, `Grep`) that fail open; every other tool — including any the wrapper doesn't recognize — fails closed. This is deliberately not a mirrored copy of the domain's risk mapping: keeping two mappings in perfect sync across a process boundary is a real ongoing maintenance risk, so the fallback is scoped to only ever be as permissive as a short, reviewable allowlist, never as permissive as the full mapping.

This allowlist applies only to unreachability. A response the wrapper cannot parse from a server it *did* reach is a different, more concerning failure mode — corruption, not absence — and always fails closed for every tool, no allowlist exception; this is the same rule `claude-code-permission-hook`'s "Malformed hook payloads fail closed" requirement already states unconditionally. (The PoC gate's throwaway spike originally routed this case through the allowlist too, which is what surfaced the need for this clarification — see `poc-findings.md` 1.4.)

**D6 — Global-persistent installation, gated by a first-use consent step.** The hook is written into user-level `~/.claude/settings.json`, not project-level, and persists across app restarts — consistent with D2 and with Phase 1's own "principal persists across every session" model. Because this is the first VaneHub feature with a side effect reaching outside the app entirely (it changes Claude Code's behavior even in a plain terminal session with VaneHub closed), the first template assignment to the `claude-code` principal requires a distinct, explicit confirmation naming that exact side effect, on top of (not instead of) the existing trusted/yolo confirmation from `permissions-approval`. Subsequent template changes, including later escalation to `trusted`/`yolo`, reuse the existing confirmation flow only — the installation consent fires once.

**D7 — `cli_config` gains an independent permission-hook projection operation.** Not folded into "apply profile" (provider/model switching) — installing or removing the `hooks.PreToolUse` entry is orthogonal to which provider Claude Code is configured against, and conflating the two would mean a provider switch could accidentally touch permission enforcement or vice versa. The new operation reuses the existing atomic-write, preserve-unrelated-keys, and fingerprint-drift machinery already proven for the provider/model projection, scoped to only the `hooks` key.

**D8 — Wrapper's own HTTP client timeout: above VaneHub's 300s sweep, below Claude Code's 600s ceiling** (a value in roughly the 310–330 second range, tuned during implementation). Reusing `ApprovalBroker`'s existing sweep means a legitimate pending `Ask` already resolves as a fail-closed `Deny` through the same channel at 300 seconds if no human responds — the wrapper's own timeout only needs to be a safety net slightly past that, comfortably clear of Claude Code's 600-second ceiling. No new timeout concept is introduced; the two existing numbers are reconciled by ordering, not by picking one over the other.

## Risks / Trade-offs

- [Risk] Global hook installation affects Claude Code usage outside VaneHub entirely. → Mitigation: D6's explicit one-time consent naming this exact effect; D5's fail-open allowlist keeps read-only Claude Code usage functional even with VaneHub closed.
- [Risk] A new local HTTP listener is new attack surface. → Mitigation: `127.0.0.1`-only, per-launch random port, bearer token regenerated every launch, no persistent credential.
- [Risk] The wrapper's offline-fallback allowlist can drift from the real `risk_level_for()` mapping over time. → Mitigation: D5's asymmetry — drift can only make the fallback more conservative (fewer recognized tools fail open), never silently more permissive, since anything unrecognized already defaults to fail-closed.
- [Risk] Claude Code changes its hook I/O contract in a future version. Real precedent: clowder-ai hit exactly this with their own PTY transcript-reading channel. → Mitigation: wrapper fails closed on any parse failure instead of crashing or hanging; the fault-injection PoC (required before implementation, per the inherited roadmap constraint) explicitly covers protocol-drift simulation, alongside server-crash and timeout scenarios.
- [Risk] `"type": "http"` hook eligibility for `PreToolUse` is unconfirmed, so there's no verified lower-overhead alternative to a fresh process per tool call yet. → Mitigation: out of scope for this design (see Non-Goals); `"type": "command"` is already confirmed sufficient to ship. Revisit only if process-spawn overhead proves to be a real problem in practice.
- [Risk] `~/.claude/settings.json` write races if a user hand-edits the file while VaneHub is applying a hook change. → Mitigation: reuse `cli_config`'s existing fingerprint-drift abort-on-conflict behavior rather than building new concurrency handling.
