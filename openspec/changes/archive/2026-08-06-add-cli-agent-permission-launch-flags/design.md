## Context

Phase 1 (`permissions-core`, archived) built a PDP generic over agent id: `evaluate(agent_id, action, resource, ...) -> Effect`, four policy templates, SQLite-backed principals. Phase 2 (`claude-code-permission-hook`, archived) wired Claude Code to it via `PreToolUse` hooks — a loopback HTTP bridge plus a spawned wrapper binary that turns every tool call into a live `evaluate()` call, centrally audited.

`gemini-cli`, `codex-cli`, and `opencode` expose no equivalent per-call interception point; this was independently confirmed against upstream docs/source and by a sibling project's (clowder-ai) own research. Fresh research this phase (against upstream docs/source directly, not paraphrased) found each tool's real capability spectrum is richer than a simple bypass flag:
- **codex-cli**: two orthogonal dials — `sandbox_mode` (`read-only` default / `workspace-write` / `danger-full-access`, OS-enforced) and `approval_policy` (`untrusted` / `on-request` default / `granular` / `never`). Headless `codex exec` hard-codes `approval_policy=Never` in source; only interactive mode can prompt.
- **gemini-cli**: a four-tier `--approval-mode` (`default` / `auto_edit` / `plan` / `yolo`), plus an independent Policy Engine, sandboxing, and trusted-folders layer. Headless mode auto-denies any prompt.
- **opencode**: a three-value `ask`/`allow`/`deny` permission model with per-tool/per-pattern granularity, a built-in `plan` agent preset that hardcodes deny on edits/subagents, and a fail-safe auto-reject for unresolved `ask` rules when run headless (`opencode run` without `--auto`).

VaneHub always launches all four managed CLIs through a real interactive PTY (`portable-pty`), never headless. This matters: each tool's own native approval prompt therefore renders and is answerable by the user inside VaneHub's terminal, the same way Claude Code's own interactive UI already does. This is the key fact that makes a real "ask every time" `standard` template viable for these three tools without building a Phase-2-style interception mechanism.

Two further discoveries during this phase's investigation shaped the design directly:
1. `src-tauri/src/contexts/tooling/cli_parameters.rs` already defines a typed, per-tool catalog of launch parameters — including permission-relevant ones (codex's `sandbox`/`approvalPolicy`, gemini's `approvalMode`, opencode's `agent`/`autoApprove`) — feeding a `selections -> preview_args -> managed_args` pipeline. It already deliberately excludes any `"dangerously-*"`-style bypass flag from every catalog (enforced by an existing test). This pipeline is reused wholesale rather than building a parallel mechanism.
2. That pipeline is currently only permission-aware for the *Chat* launch scope, via `apply_configuration_overrides` in `invocation.rs`, driven by an unrelated, pre-existing `AgentChatConfiguration.permission_mode` concept (`plan`/`agent`/`auto`, a per-message UI toggle). The *Interactive* scope (`RuntimeAgentCliProfileAdapter::load_interactive`, what Agent Terminal actually uses) has zero permission-mode awareness today. Both `cli-parameter-management` and `agent-terminal-runtime`'s existing specs currently assert the persisted CLI Parameter profile is the **single, unoverridden** argument source for interactive launches — this design requires a narrow, explicit, spec-level exception to that guarantee, scoped only to the specific parameters a policy template governs.

## Goals / Non-Goals

**Goals:**
- The four policy templates (readonly/standard/trusted/yolo) apply to `gemini-cli`, `codex-cli`, and `opencode` through the same Agent Policies page used for `claude-code`.
- `standard` genuinely enables each tool's own native interactive approval prompting, not a degraded binary choice.
- Reuse the existing `cli_parameters` pipeline; no changes to `cli_config`, no new persisted config files, no hook bridge / wrapper binary / loopback server.

**Non-Goals:**
- No dynamic per-call interception or centralized `approval_audit` entries for these three tools — their own native UI handles each decision; `evaluate()` is never called for them. Explicitly accepted asymmetry with Claude Code.
- No live-reload of an already-running terminal session when its agent's template is reassigned — takes effect on next launch only.
- No MCP-server-granular control (codex's `granular.mcp_elicitations`, opencode's per-MCP-tool rules) — templates stay at "overall posture" granularity.
- No support for these CLIs when launched manually outside VaneHub.

## Decisions

**Reuse `cli_parameters`' existing pipeline via a new override step, not new parallel infrastructure or persisted config files.**
Write `apply_policy_template_overrides(agent_id, selections, template) -> selections`, a pure function structurally mirroring the existing `apply_configuration_overrides` (same "override only the keys this concern governs, leave everything else untouched" shape). Wire it into `RuntimeAgentCliProfileAdapter::load_interactive` before its `preview_args(..., Interactive)` call. `build_interactive_invocation` itself needs no changes — it already just extends `managed_args`.
*Alternatives considered:* (a) a fully new, parallel launch-flag mechanism — rejected, duplicates an already-proven pipeline and pattern; (b) have template assignment directly `save_profile()` into `cli_parameters`' persisted selections — rejected, this would make an admin-assigned policy indistinguishable from (and silently overridable by) casual edits on the CLI Parameters page, undermining the entire point of a centrally-enforced template, and risks clobbering the user's other stored selections (model, etc.) if the merge isn't handled carefully; (c) extend `cli_config` to persist into each tool's own `settings.json`/`opencode.json`/`config.toml` (including finally onboarding gemini-cli) — rejected, reintroduces Phase 2's config-file-ownership/drift-detection complexity three more times, for a benefit (working outside VaneHub-launched sessions) that's out of scope.

**`standard` = the tool's own native ask-every-time mode.**
Because VaneHub launches interactively via a real PTY, this is achievable, not aspirational. Accepted trade-off: these decisions bypass `evaluate()` and the `approval_audit` trail entirely (see Non-Goals) — this is a deliberate, named asymmetry with Claude Code, not an oversight.

**`trusted` and `yolo` resolve identically on all three tools; no tool-specific middle tier.**
Both map to each tool's most permissive value available within its existing (non-dangerous) catalog, differing only in the assignment-time confirmation friction (`requiresConfirmationToAssign`, unchanged, already generic). This mirrors the established Phase 1 precedent that `trusted`/`yolo` already resolve identically in `evaluate()` for Claude Code — the difference has always been governance friction, not technical capability.
*Alternative considered:* give `trusted` gemini-cli's `auto_edit` mode (a genuine middle ground unique to that tool: auto-approves edits, still prompts for shell). Rejected — it would make `trusted` mean a structurally different thing depending on which tool an agent happens to be, breaking the cross-tool consistency of what each template promises.
*Accepted ceiling:* codex-cli's `sandbox` catalog option stops at `workspace-write` (no `danger-full-access`), so `trusted`/`yolo` cannot fully bypass the OS sandbox on that tool. Treated as intentional, consistent with `cli_parameters.rs`'s own existing, tested exclusion of dangerous flags from every catalog — not a gap to close.

**Gemini's `standard` must force-emit `--approval-mode default`, bypassing `preview_args`' existing "value equals the string `default` means omit the flag" convention for this one parameter.**
That convention exists for the CLI Parameters page's own "don't override, respect whatever's already configured" semantics. Gemini's own real ask-every-time mode happens to be spelled `"default"` too — a naming coincidence. Silently omitting the flag would fall through to the user's own `~/.gemini/settings.json` (which may set anything, including `yolo`), silently breaking the guarantee that `standard` reliably asks.
*Alternative considered:* accept the fallback as good enough for the common case (most users haven't customized that file). Rejected — it makes `standard`'s guarantee conditional on an invisible, unverified precondition, which is exactly the kind of fragility Phase 1-3 has otherwise avoided.

**OpenCode's `standard` needs a new environment-variable injection point.**
No existing catalog value expresses "ask before edits/bash, stay permissive for reads": opencode's own out-of-the-box default already leans permissive (mostly `allow`), unlike gemini/codex which default to asking, so — unlike those two — `standard` can't be reached here by simply not overriding anything. The generated terminal wrapper script gains one conditional line: `export OPENCODE_PERMISSION={"edit":"ask","bash":"ask"}`, added only for `(opencode, standard)`.
*Alternative considered:* approximate `standard` using only the existing `agent` enum (`default`/`build`/`plan`). Rejected as materially incorrect — none of those values reliably means "ask for risky actions," so the approximation could easily be indistinguishable from `trusted` in practice, silently failing to deliver what the template promises.

**`agent_runtime` calls into `contexts::permissions` via a direct dependency, not a new port trait.**
`RuntimeAgentCliProfileAdapter` gained a third concrete field, `permissions: PermissionsApi`, calling `find_principal` directly — mirroring how it already directly holds `CliParametersApi`/`CliApi` with no port indirection for either. This is a deliberate deviation from this decision's original plan (a new `PolicyTemplateLookupPort` trait, mirroring Phase 2's `ClaudeCodeHookPort`), discovered during implementation: Phase 2's port exists because `PermissionsApi::assign_template` — *application*-layer code — needed an abstraction for its own unit tests; this call site is already *infrastructure*-layer, the same layer as the adapter's existing direct-dependency examples, so adding a second layer of trait indirection inside it would be inconsistent with its own established style for no real benefit. `find_principal` already resolves "no explicit assignment" to the site's configurable default template (itself defaulting to `standard`, synthesized fresh on every call, no caching) — this is reused as-is, no new default-resolution logic. No circular-dependency risk (`contexts::permissions` has no reference back to `contexts::agent_runtime`).

**Template-lookup failure fails the launch closed.**
Reuses the existing `AgentRuntimeApplicationError::CliProfile` variant, the same one `load_interactive` already returns today when executable resolution fails. No silent fallback to a "safe-looking" template — consistent with this function's existing failure shape, and avoids inventing a new partially-degraded launch state.

## Risks / Trade-offs

- **[These three tools' per-call decisions bypass VaneHub's centralized audit trail entirely]** → Explicit, accepted Non-Goal, stated in both this design and the proposal; not silently glossed over.
- **[Reassigning a template has no effect on an already-running terminal session]** → Inherent to launch-time-only flags. A "restart to apply" UI hint is a reasonable low-cost follow-up but not required by this phase (see Open Questions).
- **[Narrowing `cli-parameter-management`'s and `agent-terminal-runtime`'s "single source of truth" guarantee could surprise a future reader]** → Both spec deltas state the exception explicitly and scope it only to policy-governed keys; every other parameter's behavior is provably unchanged and covered by existing plus new tests.
- **[Gemini's own catalog default for `approvalMode` is already `"yolo"` (pre-existing, unrelated fact found during this phase's research) — a user who never touched CLI Parameters already launches gemini-cli maximally permissively today]** → Out of scope to "fix" as pre-existing behavior; moot in practice once any template is assigned (even the site-wide default, which itself defaults to `standard`), since this change's override supersedes the catalog default for interactive launches.
- **[OpenCode's env-var injection is genuinely new wrapper-script infrastructure, more invasive than the flag-only changes needed for the other two tools]** → Scoped to one conditional export line for exactly `(opencode, standard)`; unit tested by asserting generated script contents; zero behavior change for every other (agent, template) combination.
- **[Cannot verify against real gemini-cli/codex-cli/opencode binaries in this development environment]** → `tasks.md` marks real-launch verification as manual/deferred, the same class of environment-limited gap as Phase 2's task 1.5 — not faked as automated coverage.
- **[Existing users see an immediate behavior change on upgrade, even if they never open the Agent Policies page]** → `find_principal` already synthesizes an effective template (the site's configured default, itself defaulting to `standard`) for every agent id, including these three — Phase 1 always intended that default to apply, it just had no enforcement point for these tools until now. A user who previously hand-tuned, say, `codex-cli`'s `approvalPolicy` to `never` in CLI Parameters will find it overridden to `on-request` (standard's mapping) the next time they launch that agent, unless they explicitly assign it `trusted`/`yolo` on the now-visible Agent Policies row. This is the feature working as intended (closing a previously-silent enforcement gap, per the proposal's Why), not a defect — but it is a real, user-visible change on upgrade and should be called out in release notes rather than discovered by surprise.

## Migration Plan

Additive only. No schema changes — reuses Phase 1's existing principal/template storage and `cli_parameters`' existing settings table unchanged. No feature flag needed: this is a deliberate, immediate rollout — every existing `gemini-cli`/`codex-cli`/`opencode` agent already has an effective template under Phase 1's rules (see the upgrade-behavior risk above), and this change simply starts enforcing it at launch time. Every CLI Parameter that a template does not govern keeps resolving exactly as today. Rollback is a plain revert — `load_interactive` returns to its current no-override behavior, nothing persisted needs undoing.

## Open Questions

- Should the Agent Policies / Agent Terminal UI show a "restart to apply" hint when a template is reassigned while that agent's terminal session is already running? Deferred — not required for this phase; worth revisiting if real usage shows it's confusing.
- Should the CLI Parameter Management page eventually show the live effective value (e.g. grey out fields a template currently governs) instead of the static help-text line this phase adds? Deferred per the earlier design discussion; revisit if the static text proves insufficient.
