## Context

**Today's native-agent mechanism** (archived `agent-tool-trust` + `agent-tool-execution`). `risk_tier_for(tool_name, input) -> ToolRiskTier` is a pure, static classifier: `shell` is always `RequiresApproval`; `file` is `AutoApprove` only for `operation: "read"`; `remember` is always `AutoApprove`; every MCP-prefixed name falls through to `RequiresApproval` by catch-all default. Since `agent-tool-trust` landed, the actual call site is a composing function, `requires_approval(tool_name, input, auto_approve_tools) -> bool`, which short-circuits `shell`/`file`-write to not-required when the agent's `auto_approve_tools` flag is set, and otherwise falls back to `risk_tier_for`. That flag lives on `agents.auto_approve_tools`, is set only through the dedicated `set_agent_tool_trust` command (with a confirmation step on enable), and is read once per generation via `ApiProviderConfig`. A pending call surfaces through a `permission_pending`-style event; the user's decision comes back through `resolve_tool_approval(session_id, call_id, approved)`. None of this has a concept of scope narrower than "forever" (the flag) or narrower memory than "this one call" (approval) — nothing in between.

**CLI agents have no equivalent at all.** Claude Code, Gemini CLI, OpenCode, and Codex CLI are launched through `agent-terminal-runtime`'s native-owned PTY wrapper. Whatever approval UI each CLI renders happens inside that terminal's own screen buffer; VaneHub does not parse it, does not record it, and does not have a lever to express "ask me before this CLI runs `rm`" beyond the per-turn `permission_mode` (`plan`/`agent`/`auto`) that `RuntimeAgentCliProfileAdapter`/`cli_profile.rs` folds into that CLI's own launch parameters. Once launched, the CLI's own permission machinery is completely opaque to VaneHub.

**Two capabilities already depend on a coarse proxy for "is this agent trustworthy."** `loop-engineering-runtime` (live) rejects an API agent as a Worker/Verifier role unless `auto_approve_tools` is enabled for it — a blunt stand-in for real scoped permission, adopted because nothing finer existed. `multi-agent-coordination` (live) has no permission-narrowing concept for sub-agents at all yet.

**No checkpoint/rewind system exists.** An external reference architecture this design draws from assumes a `/rewind`-style checkpoint mechanism to guard against "approval resolved after the thing it was approving already changed underneath it." Repository-wide search confirms `checkpoint`/`rewind` only appear in an unrelated Telegram-pagination context and a Skills filesystem-transaction context — there is no session/generation checkpoint concept in VaneHub. The staleness guard in this design is built on VaneHub's actual primitives instead (Decision 6).

**Migration precedent.** `agents.model_id`/`interface_format`/`base_url`/`auto_approve_tools` were each added by their own additive `ALTER TABLE agents ADD COLUMN ...` migration in `agent_runtime::infrastructure::schema.rs`, registered in `platform::database`'s versioned migration list (`auto_approve_tools` itself shipped as version 32, "agent-tool-trust"; the highest version currently applied is 41, "onepiece-provider-endpoints"). This change's three new tables continue that same additive pattern at version 42.

**`rmcp` (the Rust MCP SDK dependency) currently only enables the `client` feature** — VaneHub connects to external MCP servers for native-agent tool calls; it does not host one. Hosting a permission-prompt MCP server for Claude Code (Phase 2) is new capability, not something this phase needs, but the domain model here (in particular, keeping `Action` an open string) is shaped so Phase 2 doesn't need to redesign it.

## Goals / Non-Goals

**Goals:**
- One decision core (`permissions::api::evaluate`) that the native agent's tool-use loop calls for every gated action, replacing `risk_tier_for`/`requires_approval` as the approval authority while leaving `risk_tier_for` itself intact for risk-level mapping.
- Strictly more expressive than today for the native agent: three-valued `Effect` (not two), a `Scope` dimension that lets a user say "remember this for the session/project" (impossible today), and an `approval_audit` trail (nonexistent today).
- Migrate `agent-tool-trust` with a stated, testable equivalence: an agent trusted today is trusted identically the moment this change ships, with no silent behavior drift.
- Shape the schema and API so Phases 2-5 (CLI adapters, PTY fallback, delegation/budget) are additive consumers of this core, not forces that reopen its shape.

**Non-Goals (this phase):**
- Any per-CLI PEP adapter (Claude Code MCP callback, Codex/Gemini/OpenCode config compilation, PTY interception) — Phases 2-4.
- Executing delegation-chain intersection or budget/circuit-breaker logic — Phase 5 activates the fields this phase only reserves.
- Resource pattern dialects beyond exact match and workspace-relative path — richer glob/precedence dialects are Phase 3's problem, driven by real CLI config syntaxes this phase has no reason to guess at.
- Designing the `file.write` diff-preview UI, or the `yolo` template's second-confirmation copy — both explicitly deferred to implementation time.

## Decisions

### D1: `Action` is an open `String` newtype, not a closed enum
Known constants (`shell.exec`, `file.read`, `file.write`, `mcp.tool`, `memory.write`) cover Phase 1. A closed enum would force a breaking change the moment Phase 2/3 encounter CLI-native concepts this codebase can't predict yet (Codex's sandbox-escalation levels, OpenCode's `external_directory`/`doom_loop`, Gemini's tool-level model). Cost: no compile-time exhaustiveness; compensated by runtime schema validation plus unit tests over the known-constant table, mirroring how `risk_tier_for`'s existing catch-all-default pattern already accepts arbitrary MCP-prefixed names.

### D2: `Principal` reserves delegation/budget columns now, guarded inert
`agent_principals` gets `parent_principal_id NULLABLE` and `budget_config JSON NULLABLE` from the first migration; `evaluate()`'s signature is shaped around a principal *chain* (a single-node chain until Phase 5), and any attempt to set `parent_principal_id` before Phase 5 activates it is rejected with `delegation_not_enabled`. This repeats the exact pattern this codebase already used for `auto_approve_tools`, `model_id`, etc. — additive columns are cheap; the alternative (adding a parent-chain concept to `Principal` and a chain-walking signature to `evaluate()` in Phase 5) is not additive, it's a breaking signature change to code every Phase 2-4 adapter will already be calling by then.

**Correction found during implementation**: an earlier draft of this design identified `Principal` by agent id *and* session id. That's wrong and would have silently broken the migration's own acceptance criterion — the legacy `auto_approve_tools` flag (and `agent-tool-trust`'s spec before it) is scoped per-agent *forever*, across every session that agent ever participates in, not per-session. `Principal` is identified by agent id alone (one durable `agent_principals` row per agent, `agent_id` unique); `session_id` and `generation_id` are per-call evaluation context threaded alongside a principal reference into `evaluate()` and `ApprovalRequest`/`approval_audit` (needed there for `Session`-scoped grants and the D6 staleness guard), not part of what identifies the principal itself. `proposal.md` and the `permissions-core` spec are corrected to match.

### D3: The MCP floor lives inside `evaluate()`; the Plan Mode floor stays exactly where it already lives
These are not the same kind of guarantee, so they don't get the same implementation treatment:
- **MCP**: `agent-mcp-tools`'s existing spec already commits to "no automatic approval path" for any MCP-sourced call. MCP calls flow through the exact call site being rewired to `evaluate()` today (they fall through `risk_tier_for`'s catch-all to `RequiresApproval`). If MCP were just another row a policy or template could set to `Allow`, the `yolo` template — or a future admin mistake — could silently violate that existing spec commitment. `evaluate()` therefore checks `action == mcp.tool` *before* consulting any policy and floors the result at `Ask`, unconditionally, for every template including `yolo`.
- **Plan Mode**: already enforced *before* and *independent of* the approval gate — the tool catalog offered to the model excludes `shell`/MCP entirely and narrows `file` to read-only, and `execute_tool_call` separately hard-rejects any disallowed call "regardless of whether the tool appeared in the offered catalog," per the existing `agent-chat-configuration` spec, with no dependency on the approval decision either way. That check does not need to move into `evaluate()` to keep winning — it already wins by construction, at a different point in the call graph, and duplicating it inside `evaluate()` would only create two places that could drift out of sync. This phase leaves it untouched. (Implementation must verify the current call order in `api_process_adapter.rs` still holds this invariant once the `evaluate()` call site is wired in — tracked in `tasks.md`.)

### D4: Effect resolution order and template-to-behavior equivalence
Resolution order: explicit `Deny` > explicit `Allow` > default `Ask` (unmatched principal/action/resource never defaults to `Allow`). Four templates ship: `readonly` (`file.write`/`shell.exec` → `Deny`), `standard` (both → `Ask`, today's default), `trusted` (both → `Allow`), `yolo` (both → `Allow`, plus a required second confirmation at grant time — copy TBD at implementation). **`trusted` must be behaviorally identical to today's `auto_approve_tools = true`** — same tools affected (`shell.exec`, `file.write` only), same MCP/Plan-Mode exclusions — because Phase 1's migration maps every `auto_approve_tools = true` agent onto it; this equivalence is the acceptance test for the migration, not an aspiration.

**Correction found during implementation — `permission_policies` is not a table this phase needs.** A template's rules (`policies_for_template`) are a pure function of its name: no I/O, no per-installation variation, nothing to persist beyond *which* template name a principal currently has. An earlier draft of this design specified a fourth table, `permission_policies`, to store each principal's expanded rule rows — that's unnecessary duplication of data a pure function already reproduces on demand, and it's not the kind of thing D2's "pre-add now, it's cheap" reasoning actually applies to: unlike `Principal`'s constructor shape (which every future caller integrates against, so changing it later is breaking), *adding* a new table in Phase 3 once compiled/custom policies genuinely need one is exactly as cheap and additive then as it would be now — there is no later breakage this phase avoids by creating it early. `agent_principals` instead gets a `template_name` column directly, and the domain `Principal` aggregate carries a `PolicyTemplateName` field. This change now ships three tables, not four: `agent_principals`, `permission_grants`, `approval_audit`. `proposal.md` and `tasks.md` are corrected to match; a genuine `permission_policies`-shaped table (or equivalent) is deferred to whichever later phase first needs to persist non-template-derived rules.

### D5: Timeout fail-closed reuses the existing "denial reported to provider" path — no checkpoint binding
The external reference architecture this design otherwise follows closely assumes approvals can be bound to a checkpoint and invalidated on rewind. VaneHub has neither concept (see Context). A timed-out pending approval instead resolves exactly like a human denial does today: `Deny`, reported back to the provider as the tool's result, generation continues; `approval_audit` records `decider = timeout`. This is strictly simpler than "suspend and await a checkpoint that doesn't exist," and it reuses a path (`agent-tool-execution`'s existing denial-reporting scenario) that is already specified and already tested.

### D6: Staleness guard binds to `(session_id, generation_id)`, not a checkpoint
Every `ApprovalRequest` records the generation it was raised during. On resolve, the broker checks that generation is still the session's active one. `agent-tool-execution`'s existing spec already commits to ending a generation without executing a still-pending tool call when the user calls `stop_generation`; this design doesn't add a new mechanism, it adds an audit record (`decider = stale_generation`) when a resolution arrives for a generation that guarantee has already ended.

### D7: Pending queue is Rust-side source of truth; UI reconciles by pulling, not just listening
`ApprovalBroker` owns pending state; it pushes a `permission://request` Tauri event on creation, but the frontend also fetches the full pending list on mount. A push-only design would silently strand a generation waiting on approval if the window was minimized or reloading when the event fired — the exact failure mode the pull reconciliation exists to close. Pending-count visibility reuses the existing `notification-system` capability instead of a bespoke badge.

### D8: Clean cutover — no compatibility shim, no dual approval path
`resolve_tool_approval` and `set_agent_tool_trust` are removed as **Tauri commands** (the frontend-facing surface), not deprecated-in-place. `agents.auto_approve_tools` is migrated once and stops being read. The alternative — keeping the old flag/commands alive alongside the new policy engine until some later cleanup phase — was rejected: this change exists specifically to end the situation where approval state can live in more than one place with more than one audit trail, and shipping Phase 1 with two would just relocate the exact problem it's meant to close, inside a single execution path this time instead of across native-vs-CLI.

**Implementation-time refinement**: `AgentRuntimeApi`'s underlying `resolve_tool_approval` *method* (backed by `ToolApprovalPort::resolve`, which delivers a decision to the `mpsc::Sender` a blocked generation thread is waiting on) is the only mechanism that can wake that thread — it is `RuntimeAgentApiAdapter`-private in-memory state (`ManagedApiGeneration.pending_approvals`, keyed by `call_id` within a `process_id`), which `permissions` cannot own or reach into without an inbound dependency `agent_runtime` already forbids in reverse. It stays, `pub(crate)` within `agent_runtime`, called by the *new* `permissions` command handler rather than exposed as its own Tauri command. That handler is the one place allowed to hold both context facades (a command adapter, not a domain), and it already gets a free correctness property from this: `ToolApprovalPort::resolve` returns `Ok(false)` whenever `process_id`/`call_id` is no longer present in `RuntimeAgentApiAdapter`'s map — which is exactly and only true once that generation has already ended — so D6's staleness check does not need `permissions` to independently know anything about generation liveness; a `false` return *is* the staleness signal, recorded as `decider = stale_generation`.

### D9: `RiskLevel` is a fixed function of `Action`, not independently configurable
Phase 1's mapping is fixed and total: `file.read` and `memory.write` → `L0`; `file.write` → `L1`; `shell.exec` → `L2`; `mcp.tool` → `L2` (for audit/display consistency only — per D3, its floor is `Ask` regardless of level, so its level never changes what it resolves to). `L3` is declared but unused in Phase 1 (reserved for a future network/external-effect category Phase 3 or later may need). This mapping lives next to the `Action` constants in `domain/`, as a pure function, not as a per-policy-row configurable field — a template can change what happens at a given risk level (via its `Effect` for that action), but it cannot change which level an action *is*. Keeping the mapping fixed avoids a second, independent axis of misconfiguration (a `readonly` template that someone miscategorizes `shell.exec` as `L0` under would silently defeat the template's own intent); if a real need for per-installation risk recalibration surfaces later, it's a narrow, additive follow-up, not something Phase 1 needs to anticipate.

## Risks / Trade-offs

| Risk | Mitigation |
|---|---|
| Action/Resource taxonomy chosen for the native agent turns out to not fit a CLI's native concepts once Phase 2/3 actually map them | D1's open-string design; a paper mapping table (per-CLI concept → VaneHub `Action`) is a prerequisite gate before Phase 3 implementation starts, not guessed at now |
| Migration silently changes an already-trusted agent's behavior | `trusted`-template equivalence (D4) is enforced by a dedicated regression test asserting `shell.exec`/`file.write` → `Allow`, `mcp.tool` → `Ask`, Plan Mode still hard-rejects, post-migration |
| `evaluate()` adds a synchronous SQLite read to every gated tool call | Kept in-process (no network hop); if this proves measurably slow, caching is a follow-up, not a Phase 1 concern — no evidence yet that it will be |
| Removing `resolve_tool_approval`/`set_agent_tool_trust` breaks a caller outside this migration | Both are internal frontend-service-boundary calls only (`agent-service.ts` and its Tauri/Web clients); no external/public API surface exists for either, so the cutover is a single coordinated change |
| MCP-floor and Plan-Mode-floor logic live in two different places (D3) and could drift apart in someone's mental model even though they don't drift in code | Both are documented here explicitly as permanent, template-proof invariants; architecture/unit tests assert both independently of whichever templates exist |

## Migration Plan

1. Add migration version 42: create `agent_principals` (including its `template_name` column), `permission_grants`, `approval_audit`.
2. Backfill: for every row in `agents`, create its `agent_principals` row with `template_name = 'trusted'` if `auto_approve_tools = 1`, else `'standard'`.
3. Land the `evaluate()` call-site swap, command removal (`resolve_tool_approval`/`set_agent_tool_trust` → new `permissions` commands), and UI swap (trust toggle → template picker) in the same change — no intermediate state where both mechanisms are live.
4. Gate: migration-equivalence regression test (D4/Risks) must pass before this change can be archived.
5. Rollback: the migration is purely additive (no column drop in this phase — see Open Questions), so reverting the cutover commit alone restores prior behavior without a destructive down-migration.

- Whether `agents.auto_approve_tools` is physically dropped in this phase's migration or left inert for a later cleanup — left to `tasks.md`.
- `file.write` approval-card diff-preview presentation — deferred to implementation, as already scoped in `proposal.md`.
- Whether `yolo` needs its own second-confirmation modal copy/flow beyond what `trusted`'s existing confirmation pattern provides — mirrors an open question the reference architecture this design follows also left unresolved; default assumption for Phase 1 is yes, a distinct (stronger-worded) confirmation, finalized at implementation.

## Roadmap (Phases 2-5, outline only — each detailed at its own implementation time)

- **Phase 2 — `add-claude-code-permission-callback`**: add the `server` feature to `rmcp`; host a permission-prompt MCP tool; inject `--permission-prompt-tool` at Claude Code launch; project-layer `settings.json` snapshot/restore around the session. Carries forward two decisions from the reference architecture unchanged, since neither depends on anything VaneHub-specific: the callback's own await-timeout must stay shorter than Claude Code's MCP client timeout, and a fault-injection PoC (server crash, timeout, protocol drift) is a prerequisite gate before implementation.
- **Phase 3 — `add-policy-compiler`**: compiles unified policies to each CLI's native config dialect (Codex `config.toml` + `.rules`, Gemini launch-parameter injection, OpenCode `serve`+SSE), every rule tagged with a fidelity level (`exact`/`narrowed`/`runtime_only`), differential testing (compiled CLI allow-set ⊆ PDP allow-set) as an archive gate. Reuses `cli-agent-config-management`'s already-built project-layer snapshot/atomic-replace/compensate machinery rather than reinventing it.
- **Phase 4 — `add-pty-interception`**: a screen-state (not raw-byte-stream) recognizer layered onto `agent-terminal-runtime`'s existing PTY/vt100 pipeline, for the residual cases Phase 3 can't statically express. Fail-safe takes priority over recognition accuracy: unrecognized state always degrades to human handoff, never a guessed keystroke injection.
- **Phase 5 — `add-agent-delegation-budget`**: activates this phase's reserved `parent_principal_id`/`budget_config` columns; a sub-agent's effective permission becomes the intersection of its own policy and its parent chain's; replaces `loop-engineering-runtime`'s current blunt `auto_approve_tools`-required gate for Worker/Verifier roles with real delegation-scoped permission. **Explicit open question, not answered by this roadmap**: the reference architecture this design otherwise follows assumes interrupting a loop at risk-tier L2+ can "drop a checkpoint and hand off to `/rewind`" — VaneHub has neither, so Phase 5 needs its own design for what a loop-interruption boundary means here before that phase starts.

### Roadmap refinement — external validation against clowder-ai (2026-08-05)

A comparable project (`clowder-ai`, a Node/Electron desktop app also orchestrating Claude Code/Codex CLI/Gemini CLI/OpenCode) was reviewed for prior art on exactly the PTY-interception question Phase 4 raises. Findings, and what they change about this roadmap:

- **Phase 2's premise is reinforced, not weakened**: clowder-ai found exactly one CLI (Claude Code) worth building a live per-call permission callback for; the other three are launched with static bypass flags instead (`approval_policy`/`--dangerously-skip-permissions`/`--yolo`-equivalent), because none of them expose an equivalent runtime callback. This matches Phase 2 singling out Claude Code and should be treated as corroborating evidence, not just an assumption, when Phase 2 actually starts.
- **Phase 3 may be over-scoped as currently written**: a full policy-compiler-plus-differential-testing apparatus is only necessary for CLIs that need per-call `Ask` semantics (the `standard` template) reproduced statically — and clowder-ai's experience suggests Codex/Gemini/OpenCode currently offer no live decision channel to reproduce that against at all. The `readonly`/`trusted`/`yolo` templates, by contrast, only need a static launch-time flag decision (no differential testing, no compiler) — closer to what clowder-ai actually ships. Whoever starts Phase 3 should re-derive its scope from this distinction rather than assume the originally-sketched compiler is the right shape for all four templates uniformly; `standard` for these three CLIs may need to be explicitly documented as unsupported rather than solved.
- **Phase 4 should default to human handoff, not recognition**: clowder-ai's only production use of raw PTY-text scanning is a single hardcoded substring match dismissing a one-time onboarding dialog — not a general approval-prompt interpreter — and they suffered a real incident from depending on CLI-specific terminal text (a Claude Code version upgrade silently broke it, mitigated by pinning an old binary). Their stated principle, repeated across their own design docs: PTY carries input injection and human observation; output/event semantics must come from a structured side-channel or not be attempted at all. Their actual fallback tier for whatever their static-flag approach can't cover is not automated prompt-answering — it is a human watching a live terminal and typing themselves. This roadmap's existing "unrecognized state always degrades to human handoff" line should be read as the *dominant* posture for Phase 4, not an edge-case fallback within a mostly-automated recognizer: default to surfacing the live terminal to a human, and treat automated recognition as justified only for the same narrow class of case clowder-ai used it for (single, rarely-changing, low-risk prompts), not as Phase 4's primary mechanism.

None of this changes Phase 1's already-shipped scope. It is scoping input for whoever starts Phase 2/3/4, to be revisited — and re-verified against each CLI's actual current behavior, not just this note — at that time.
