# 本地媒体运行时

`local_media` 上下文提供四项输入框能力——识别图片或 PDF 中的文字、截取屏幕区域并识别文字、按住说话转写、朗读文本——以及 OnePiece `ocr_read_text` 的原生工具路径。四者全部在用户本机运行。

## 选择图片与截取屏幕

图片/PDF 按钮会打开普通文件选择器。截图按钮会先隐藏 VaneHub、冻结各个可用屏幕，再打开全屏区域选择层。拖动选择一个矩形；也可以按 **Esc**、点击右键或点击取消按钮退出。选中的 PNG 会进入与图片文件相同的可编辑 OCR 复核流程，识别文本绝不会被自动追加或发送。

截图只在桌面客户端且 OCR 已就绪时可用；Web 模式与单 Agent CLI 终端会明确保持不可用。macOS 可能要求开启「屏幕录制」权限；Linux 是否可用取决于当前 X11 或 Wayland 合成器。截图像素始终留在本机，不进入日志，并在成功、取消、超时、切换会话或退出程序时释放。

## 本功能不做的事

这是理解该功能形态最短的一条路径：

- **它不会安装任何东西**。不下载、不内置、也不在首次使用时拉取 Python 解释器、推理包、CUDA 运行时或模型。设置页没有下载按钮，因为按钮背后没有任何东西。
- **它没有云端兜底**。未配置或无法工作的引擎会被报告为不可用，绝不会被悄悄替换成托管服务。
- **它不打包模型权重**。随产品分发的是 `src-tauri/resources/local-media-worker/vane_local_media_worker/` 下约 200 KB 的 Python 源码。若该目录出现任何非 `.py` 文件，架构测试会让构建失败。

## 需要用户自行准备的部分

三个引擎在**设置 → 本地媒体**中各自独立配置，可以分别指向不同的 Python 环境。

| 引擎 | 依赖包 | 还需要 |
| --- | --- | --- |
| 文字识别 | `paddleocr`（以及 `paddlepaddle`） | PaddleX 产线配置文件，或者文本检测与文本识别两个模型目录 |
| 语音转写 | `faster-whisper` | 已下载到本机的 faster-whisper 模型目录 |
| 语音合成 | `sherpa-onnx` | `.onnx` 语音模型及其 `tokens` 文件，以及该模型类型所需的辅助文件 |

路径必须是绝对路径。`Path::is_absolute` 是有意按平台判定的：携带另一操作系统路径的配置会在校验阶段被拒绝，而不是在模型加载器内部三层之下才失败。

CUDA 可以选择，但从不由本产品提供。选它意味着本机已装好匹配的驱动与运行时。

## 工作进程桥接

每个引擎一个 Python 进程，首次使用时惰性启动，之后保持存活。宿主与工作进程通过 stdin/stdout 交换每行一个 UTF-8 JSON 对象，协议版本为 1。

这条通道上有几项性质是承重的，而非顺带的：

- **stdout 只承载协议帧**。`install_stdout_guard()` 会在导入任何引擎之前把 `sys.stdout` 指向 stderr，这样某个库打印进度横幅也无法污染流。格式错误的行被视为污染，工作进程随即被终止。
- **参数以参数向量传递**。全程不经过任何 shell，也没有任何工作进程模块导入 `subprocess`——两者都有测试强制。
- **派发始终留在主线程**。推理跑在工作线程上，因此模型加载或运行期间仍然读得到 `cancel` 帧。
- **帧有大小上限**。入站 1 MiB、出站 8 MiB，按编码后的字节计。超限的响应会变成协议错误，而不是一个看起来完整的截断结果。
- **同一时刻只有一次推理**。运行期间到来的第二个请求会被 `ENGINE_BUSY` 拒绝，而不是排在一次看不见的模型加载后面。

## 离线姿态的准确表述

工作进程环境会移除代理变量，并设置 `HF_HUB_OFFLINE=1` 与 `TRANSFORMERS_OFFLINE=1`。faster-whisper 以 `local_files_only=True` 打开；PaddleOCR 的每个可选子模型在未配置本地目录时都显式传 `False`——对 PaddleOCR 而言，省略某个模型参数并不是中性的默认值，而是一次下载。

**以上描述的是本功能自身的代码路径**，并不是在宣称操作系统层面阻止了任意 Python 包打开套接字。桥接层的测试套件会禁用全部套接字构造函数，并证明工作进程自身的路径照常完成；这就是本功能做出的保证，也正是设置页所陈述的那一条。

## 数据本身的隐私

音频从不进入 React 状态，也不经过 Tauri 的 JSON IPC。采集、WAV 编码、播放、临时文件与工作进程监管全部留在 Rust 侧。渲染层对所选文件只知道一个不透明的暂存输入 id 和一个显示名；宿主路径只在文件选择器处使用一次，绝不回传。

日志排除音频字节、识别文本、转写文本、合成输入、完整路径、完整协议帧与原始 traceback。工作进程诊断由标量白名单构成，捕获到的异常只贡献其类名——模型加载器经常把模型路径放进 `str(exc)`，因此消息在工作进程内就被丢弃，而不是留到宿主边界再处理。

## 就绪状态按引擎独立

一台装好 PaddleOCR 但没有麦克风的机器，文字识别照常可用。每张引擎卡片拥有自己的开关、就绪状态与检查按钮，不读取另外两个的任何状态。

检查针对**已保存**的配置执行，绝不针对草稿：一次探测会用真实模型路径启动真实的工作进程，为用户尚未提交的文本回答「这样配对不对」，等于为一份并不存在的配置报告就绪。

连续启动失败会让该引擎的工作槽进入隔离，而不是形成重启循环。它会一直保持隔离，直到用户重新检查或保存新配置。

## PaddleOCR 归谁所有

`local_media` 是 PaddleOCR **推理进程、模型生命周期、readiness、inference、取消、超时、结果与资源限制**的唯一生产运行时归属方。

这句话的范围是刻意收窄的：仓库里还有一处提到 PaddleOCR，值得把它到底做什么讲准。扩展能力页（`tooling/extensions`）把 PaddleOCR 列为**可安装的外部依赖**——创建受管 Python 环境、安装 `paddleocr` 与 `paddlepaddle`、记录已安装版本、探测一个 loopback 存活性 sidecar。上面列出的那些它一样都不拥有；若它开始声明 inference 协议或反向依赖 `local_media`，架构测试会让构建失败。

OnePiece 的 `ocr_read_text` 工具通过适配器访问本上下文，自身从不接触 PaddleOCR。该工具的契约未变（`contractVersion: 1`、仅接受工件输入），其就绪状态由本地媒体状态推导，而不是另存一份引擎自身的健康信息。

通过扩展页安装该包、再把本页的 **Python 解释器**字段指向那个受管环境，是一种受支持的配置方式。这不会转移任何归属：worker 依然在这里启动、监管、限界与取消。

## 如何验证

- `npm run local-media:python:test` 运行桥接层测试套件。它只用 Python 标准库；在找不到解释器时报告 `NOT RUN` 并给出原因，绝不报告通过。
- Rust 测试套件以 fake 覆盖准入、暂存、监管进程、采集与播放。
- Web 模式的 Playwright 覆盖断言浏览器构建保持可见且有据可循的不可用状态，而不是模拟成功。

### 这些验证能与不能说明什么

核心代码路径与确定性自动化测试已经实现并通过。针对真实 PaddleOCR、faster-whisper、sherpa-onnx 模型的冒烟测试，真实麦克风与扬声器硬件，以及开发者本机以外的目标平台验证，仍然是 **NOT RUN 或 BLOCKED**。「测试通过」是对代码路径的陈述，不等于三项能力已经对真实引擎做过端到端验证。`smoke.py` 正是为这段缺口准备的，在引擎未安装前会逐引擎报告 `NOT RUN`。
