# Skill 覆盖层治理

Skill 覆盖层(Overlay)在不编辑 Skill 权威包的前提下,定制其生效指令与支撑资源。每一次改动都可归因到某个 Overlay 修订,可在提交前预览,并且可在不复制或重写基础 `SKILL.md` 的情况下被禁用、回退或调和。

## 覆盖层作用域不是 Skill 层

生效的 Skill 目录首先按规范 Skill id 选定一个基础包。包层依次从 Project 解析到 User、Registry、System。覆盖层重放(replay)只在该胜出者被选定之后才开始。

覆盖层作用域回答的是定制应用在何处:

| 覆盖层作用域 | 应用于 | 重放顺序 |
| --- | --- | --- |
| System | 所有管理上下文 | 第一 |
| User | 当前用户跨工作区 | 第二 |
| Project | 一个规范工作区 | 最后 |

一个 Overlay 可以指向来自任意层的基础包。对 System 包施加的 Project Overlay 不会把该包变成 Project 包,System Overlay 也不会让不可变包变得可编辑。在没有活动工作区时,Project Overlay 会被排除。

因此,UI 会分别报告基础层和活动 Overlay 作用域。Agent 绑定继续引用规范 Skill id,并且只消费最终治理后的生效视图。

## 存储边界

Overlay 清单存储的是变更和基础见证(witness),而非完整的包副本。支撑载荷采用内容寻址,历史是仅追加(append-only)的。

```text
~/.vanehub/skill_overlays/<skill-id>.json
~/.vanehub/skill_overlays/user/<skill-id>.json
~/.vanehub/skill_overlays/.payloads/
~/.vanehub/skill_overlays/history/<skill-id>/

<workspace>/.vanehub/skills/.overlays/<skill-id>.json
<workspace>/.vanehub/skills/.overlays/.payloads/
<workspace>/.vanehub/skills/.overlays/history/<skill-id>/
```

System 与 User 清单路径各自独立,但共享 home 下的载荷与历史根。Project 状态保留在其规范工作区内部。保留的载荷、历史、事务与隔离目录被排除在 Overlay 发现范围之外。

调用方通过 `references`、`templates` 或 `assets` 下的逻辑路径来寻址资源,它们绝不会收到可变的载荷路径。绝对路径、父级穿越、隐藏分量、保留设备名、备用流、逃逸出边界的链接,以及可执行或脚本内容,都会在持久化之前被拒绝。

## 信任与校验

一个本地变更只有在其内容、路径、媒体类型、大小、见证以及重放结果都通过校验之后,才会被信任。导入的 ZIP v1 包会在隔离的隔离(quarantine)目录中被扫描,然后以不可信状态存储。在用户审查并提升其精确修订和文档哈希之前,它不能影响指令或资源。

提升会重新执行扫描、载荷校验、基础比对和重放。已变更的修订、文档哈希、基础见证、载荷、扫描结果或 pin 状态都会让审查变得过期。对于私钥材料、凭证结构、提示词权威覆盖、可执行标记,或伪装成可执行内容等硬拒绝(hard-deny)发现,不存在任何覆盖手段。

校验和拒绝诊断使用统一日志服务。日志中只包含安全的规则 id、哈希、大小和脱敏后的身份信息,而不是提交的指令或携带机密的内容。

## 确定性重放与回退

重放在一个不可变的生效包快照上操作:

1. 校验规范身份、基础与包哈希、信任状态、文档修订,以及载荷哈希。
2. 从选定的基础指令和资源开始。
3. 依次重放 System、User,以及匹配的 Project 作用域。
4. 在一个作用域内,按创建顺序应用活动的精确补丁,在一个固定的分隔符下追加活动的习得指导块,并按逻辑路径合并资源。
5. 发布最终的指令、资源视图、各作用域哈希、影子摘要,以及冲突状态。

精确补丁使用 Unicode 字符串相等性判断,不做模糊匹配或空白归一化。非 `replace_all` 补丁要求恰好一处匹配;`replace_all` 补丁要求至少一处匹配。

如果某个作用域出现冲突或完整性失败,其整个暂态结果会被丢弃。运行时会保留上一个健康的较低作用域结果,并把依赖它的较高作用域标记为阻塞。不可信的导入和未解决的漂移也会被排除。eager 提示、`load_skill`、资源读取、预览,以及 CLI 衍生的挂载,都消费这同一个最近健康的生效快照。

当基础指令或包哈希发生变化时,Overlay 进入调和状态。即使是干净的重放,也要求用户在接受新的见证之前审查新的完整 diff。冲突的变更可以被编辑或忽略;忽略会禁用该变更,同时保留其记录与历史。

## Pinning

Pinning 冻结已提交的生效行为。在 pinning 之前处于活动状态的健康 Overlay 修订会继续重放,但每一个可能改变 Overlay 状态的操作都会被拒绝,包括创建、导入、提升、打补丁、追加指导、文件改动、禁用、回退,以及调和。

在 pinned 期间,漂移仍然可见。用户必须先显式 unpin 才能去解决它。一次 pinned 拒绝不会推进修订、追加历史,或更新使用计数器。

## 强制限制

默认的 Overlay 边界强制执行:

| 项目 | 限制 |
| --- | --- |
| 合并后的指令变更文本 | 65,536 字符 |
| 一个 Overlay 中的变更数 | 256 |
| 逻辑资源路径 | 240 字符且 8 个分量 |
| 导入归档条目数 | 512 |
| 支撑文件 | 1 MiB |
| 压缩的导入包 | 8 MiB |
| 展开后的导入内容 | 32 MiB |
| 活动历史段 | 4 MiB |

导入必须包含一个根 `overlay.json`,并且只能有它声明过的 `payloads/sha256/<lowercase-sha256>` 条目。重复、缺失、未声明、加密、链接、穿越、哈希不匹配、大小不匹配或不支持的条目都会导致整个导入被拒绝。

## 原子提交与恢复

每次变更都需要提供预期的 Overlay 修订和生效基础哈希。预览与提交使用相同的准备流水线,但提交会重新检查在线见证,以缩小 time-of-check/time-of-use 间隙。过期请求不会持久化任何部分状态;UI 会保留未保存的输入,并要求一次新的预览。

在一个每 Overlay 锁下,一个可恢复的事务暂存下一个清单、可达载荷、一个关联的历史事件,以及使用计数器的变更。提交前的失败会恢复到完整的上一修订。提交决策之后的失败会在恢复期间完成完整的下一修订。运行时绝不会接受清单、载荷、历史与使用状态的混合体。

历史事件和段构成一条校验链。一个段在达到 4 MiB 之前会滚动翻页。缺失、截断或被篡改的历史会被报告为完整性失败,绝不会静默修复或省略。回退会创建一个新的修订和事件;它不会删除原始变更或审计记录。

运维人员不应手动编辑清单、载荷、事务标记或历史文件。恢复与调和必须通过 Skill 应用服务进行,以保证哈希、见证、历史与使用计数保持一致。

## 运行时边界

原生 `tooling::skills` 应用服务拥有 Overlay 的发现、校验、重放、事务与恢复。React 组件使用 `agent-service.ts`;只有 Tauri 适配器调用原生命令。Web/mock 适配器对相同的修订、过期见证、隔离、pinning、冲突、历史与回退行为建模,但不声称具备原生文件系统持久化。
