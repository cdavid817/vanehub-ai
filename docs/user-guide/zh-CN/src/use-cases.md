# 使用案例

四个端到端场景。每个都只使用**已交付**的功能。

---

## 案例一：双 Agent 并行处理同一仓库的不同任务

**背景**：一个仓库里有两件互不相干的事——修一个 bug、补一批测试。你想同时推进，又不想让两个 Agent 互相干扰。

**目标**：两个 Agent 各自独立作业，上下文互不污染。

### 操作流程

1. 点击**新建**，**会话类型**选**单 Agent**，选择 **Claude Code**。
2. **工作区**选**本地**，选定项目目录。因为是 Git 项目，勾选**创建新 Git worktree**，命名 `fix-bug`。
3. 填写标题「修复登录超时」，创建。
4. 再次点击**新建**，这次选择 **Gemini CLI**。
5. 同一个项目目录，同样勾选**创建新 Git worktree**，命名 `add-tests`。
6. 填写标题「补充认证模块测试」，创建。

### 结果说明

两个会话各自在**独立的 Git worktree** 中作业，分支互不影响，文件改动不会冲突。

worktree 默认建在**项目的同级目录**，分支名形如 `vanehub/<worktree名>`。

在会话侧边栏可以随时切换，两个会话的**变更**标签分别显示各自 worktree 的 Git 状态。

> **注意**：两个会话共享同一套权限模板与个性化设置。如果只想放宽其中一个的权限，需要在 **Agent 权限策略**里按 Agent 单独配置。

## 案例二：用 Loop 把「改代码 → 跑测试」自动化

**背景**：一次重构后有若干测试失败，你不想一轮轮手工「让 Agent 改 → 自己跑测试 → 把失败贴回去」。

**目标**：让 Agent 自己迭代到测试全绿，但最终由你确认。

### 操作流程

1. 左侧活动栏选择**循环工程**，新建定义。
2. **目标**填写：「修复 `src/auth` 下的失败测试，不改动测试文件本身」。
3. **限额**设置：
   - 迭代上限 `8`
   - 单步超时 `600` 秒，总超时 `3600` 秒
   - 连续无进展容忍 `2` 次
4. **验收命令**添加两条：
   - `npm run lint:ci`
   - `npm run test`
5. 保存并启动。
6. 在时间线视图观察每轮的阶段流转，在迭代详情里看每轮的检查结果。
7. 运行进入**待人工验收**后，检查产出并确认。

### 结果说明

每轮按「准备 → 行动 → 验证 → 判定 → 收尾」推进。**必过检查未通过时，即使 Agent 认为已完成也会继续下一轮**。

如果连续两轮代码变更、失败检查集合、通过检查集合**三者都没变化**，会以「无进展」终止——避免在死胡同里空转。

**Loop 永远不会自己宣布成功。**即使判定目标已达成，也只会停在待验收状态等你确认。

> **限制**：Loop 在独立 worktree 中作业，因此**不适用于远程工作区**；迭代上限硬性封顶 20。

## 案例三：为敏感操作配置审批并处理一次审批

**背景**：你要让 Agent 在一个生产配置仓库里工作，希望它能自由阅读，但任何写入和命令执行都必须经你确认。

**目标**：配置最小权限，并走通一次审批。

### 操作流程

1. 打开**设置 → Agent 权限策略**。
2. 把目标 Agent 的模板设为**标准**。
   - 如果要更严，选**只读**——但注意只读会**拒绝**写文件与执行命令，Agent 无法完成任何修改类任务。
3. 回到会话，给 Agent 一个需要改文件的任务。
4. Agent 尝试写文件时，执行会中断并弹出审批请求。
5. 查看请求的动作与目标，选择**批准**。
6. 选择记忆范围：
   - 选**仅本次**——下次写文件还会再问
   - 选**本项目**——这个项目里同类动作不再询问

### 结果说明

「标准」档位下，**读文件始终放行**，写文件与执行命令每次询问。

每一次判定都会写审计记录，包括直接放行和直接拒绝的，事后可以回查是谁在什么时候批准了什么。

> **两点容易误解**：
> - **「只读」不是禁止一切**——读文件与写记忆照常放行。
> - **「信任」与「Yolo」的实际策略完全相同**，区别只在切换时的确认强度。

## 案例四：用定时任务 + IM 做每日自动体检

**背景**：你希望每天早上自动跑一轮代码质量检查，结果推到团队群里，不用自己盯着。

**目标**：无人值守地跑检查并获得通知。

### 操作流程

1. 先配好 IM：**设置 → IM 能力**，选择飞书（或钉钉 / 企业微信），填入开放平台创建的应用凭据。
2. 左侧活动栏选择**定时任务**，新建任务。
3. 频率选**每天**，时刻设为 `09:00`。
4. 配置任务要执行的内容（目标仓库与检查任务）。
5. 保存并**启用**。

### 结果说明

任务按**你本地时区**的每天 9 点触发，自动创建会话执行。

执行结果可以通过 IM 连接器回到群里；你也可以直接在群里发消息驱动 Agent，由连接器创建的会话会被标记来源。

在**链路**标签中，这类执行会标注「由定时任务触发」并带任务标识，方便反查是哪个任务跑的。

> **关键限制**：**应用完全退出后定时任务不会触发**。调度器在应用内运行，不是系统级服务——需要无人值守时请保持应用运行。

## 案例五：用链路视图排查一次失败的执行

**背景**：一次 Agent 执行失败了，输出里只有一句语焉不详的报错。

**目标**：定位失败发生在哪一环。

### 操作流程

1. 打开该会话的**链路**标签。
2. 从根节点往下看四层结构：会话 → Agent → 工具/MCP 边界 → 进程执行。
3. 找到状态为失败的节点，查看其耗时与错误分类。
4. 如果失败节点是**不透明**保真度，说明它是外部 CLI 的内部行为，链路到此为止——转到**终端记录**或**日志**标签继续看。
5. 在**日志**标签用关键词搜索，或用**定位**跳到失败发生的时间点附近。

### 结果说明

链路能告诉你**哪一环慢、哪一环挂**；日志能告诉你**具体报了什么**。

> **两者不能交叉检索**：日志中刻意不包含链路标识符，这是隐私设计。你需要用**时间**把两边对上，而不是用 id。

如果你用的是 [OnePiece](native-agent.md)，链路信息量会明显更高——它的工具调用是原生保真度，可以逐层展开；外部 CLI 只能看到边界。
