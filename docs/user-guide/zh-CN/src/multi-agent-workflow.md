# 多 Agent 群聊与 `@` 交接

**状态：已交付——桌面端运行时；席位分配在正常的创建会话对话框中可见。**

## 功能概述

一个会话可以容纳多个 Agent **席位（Seat）**。每个席位是「一个 Agent + 一个专家角色」的组合，所有席位读同一条共享对话线索。Agent 在回复中用 `@` 点名，把发言权交给下一位，也可以交还给你。

这解决的是「多个 Agent 协作时，上下文要手工搬来搬去」的问题。

## 分配席位

1. 打开 VaneHub AI，选择**新建**。
2. 在席位区为每个要参与的 Agent 添加一个席位。
3. 为每个席位指定**专家角色**。角色名会派生出其他席位 `@` 时使用的**句柄**。
4. 选择项目目录，填写会话标题，创建会话。

![创建会话对话框中已选中多 Agent 会话类型，显示席位分配区](../assets/screenshots/create-session-multi-agent-zh-CN.png)

内置三个专家角色可直接使用，也可以在**设置 → 专家角色**中自建。

## 交接发言权

在回复中输入 `@` 会触发席位补全，选择目标席位的句柄即可把发言权交过去。当前发言权归属显示在轮次状态栏。

**句柄的派生规则**：

| 情况 | 结果 |
| --- | --- |
| 角色名含空白 | 空白变成 `-`，例如「代码 审查」→ `代码-审查` |
| 两个席位同角色名 | 第二个自动加后缀，例如 `评审-2` |
| 席位未分配角色 | 没有可被 `@` 的稳定句柄 |

**几条不会误触发的保护**：

- **围栏代码块内的 `@` 会被忽略**，粘贴含 `@reviewer` 的示例代码不会触发交接。
- 引用符号与列表标记（`>`、`-`、`*`、`+`、有序编号）不影响识别——写清单时仍然是在对人说话。
- 席位**不能把发言权交给自己**；同一目标提两次只算一次。
- 一次回复没有提及任何人时，本轮**正常结束**，不是失败。

## 交还给你

Agent 可以用 `@用户` 把发言权交回来，三种写法效果不同：

| 写法 | 效果 |
| --- | --- |
| `@用户 handoff` | 发言权归你，本轮等待你处理 |
| `@用户 done` | 本轮完成 |
| 单独的 `@用户` | 仅知会，流程继续，不打断 |

**只有 `handoff` 会打断流程。**单独提及被有意做得很轻量——如果每次提到你都要停下来等，Agent 会学会干脆不提，反而让你失去可见性。

## 链路上限

运行时对**一次回复中的提及数量**和**交接链路的深度**都设了上限。Agent 之间是自主提及的，没有上限时两个 Agent 可能无限来回。

**触及上限时会显示具体原因**，而不是让链路悄无声息地停下——否则你会疑惑为什么没人回应。

## 注意事项与限制

- **多 Agent 执行依赖桌面端运行时。**在 Web 预览中席位控件可以渲染，但不会启动任何 CLI 进程。
- **共享线索不等于共享会话。**各 Agent 在自己的会话里仍保有各自历史，VaneHub AI 不会合并它们的原生会话文件。
- **`OpenCode` 没有固定的模型族。**它驱动的是你自己配置的模型，因此「要求评审来自不同模型族」这类策略对它不生效。
- 群聊与 [Loop 工程化](loop-engineering.md) 是两套不同机制：群聊由 Agent 自己 `@` 决定下一位，Loop 由运行时按阶段自动推进。
