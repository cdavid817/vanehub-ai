# 反馈问题与提交 Issue

## 先确认该不该提

提 Issue 之前先过一遍这三步，能省掉大部分来回：

1. **查[故障排查](troubleshooting.md)**——「CLI 显示未安装」「会话停在需要处理」这类高频问题都有现成答案。
2. **查[常见问题](faq.md)**——如果你的疑问其实是「这个功能是不是本来就这样设计的」，答案多半在这里。
3. **搜已有 Issue**——[仓库 Issue 列表](https://github.com/cdavid817/vanehub-ai/issues)。搜索是 bug 表单里的必勾项，别跳过。

VaneHub AI 是**社区支持**的项目，没有商业工单渠道。

## 挑对入口

仓库**关闭了空白 Issue**，必须从下面四个入口之一进：

| 你要报的 | 去哪 |
| --- | --- |
| **可复现的缺陷** | [Bug report 表单](https://github.com/cdavid817/vanehub-ai/issues/new?template=bug.yml) |
| **功能建议** | [Feature request 表单](https://github.com/cdavid817/vanehub-ai/issues/new?template=feature.yml) |
| **安全漏洞** | [私有安全公告](https://github.com/cdavid817/vanehub-ai/security/advisories/new) |
| **不确定算不算问题** | 先读 [SUPPORT.md](https://github.com/cdavid817/vanehub-ai/blob/main/SUPPORT.md) |

> **安全漏洞不要开公开 Issue**。走私有安全公告通道，流程见仓库的 `SECURITY.md`。公开 Issue 不是合适的安全报告渠道——bug 表单里那句「This is not a security vulnerability」是必勾项，正是为此。

## 报缺陷：表单要什么

Bug 表单有四个必填项，缺一个都会让问题变得难以处理。

### 1. 版本或 commit

填应用版本号（如 `v0.1.0`）或 commit SHA。

**从哪拿**：**设置 → 关于**，那里有版本号、更新检查与 changelog 链接。

### 2. 操作系统

三选一：**Windows**、**macOS**、**Linux**。

**桌面端的行为不能外推到其他平台**。同一个现象在三个系统上的成因可能完全不同（`PATH` 解析、凭据存储、文件锁），所以这一项必填。只在一个系统上出现的问题，请写明你在另外哪些系统上验证过。

### 3. 发生了什么

**同时写实际行为和期望行为**。只写「不工作」无法定位；「我以为会 X，实际是 Y」才可以。

### 4. 复现步骤

按编号写，从打开哪个界面开始：

```text
1. 打开 设置 → CLI 管理
2. 对 Claude Code 点「升级」
3. 观察到版本号没有变化
```

**步骤越短越好**。能用一个新建的空项目复现，就别用你的真实仓库。

### 5. 脱敏后的诊断信息（选填但强烈建议）

日志、截图、各 Agent CLI 的版本号。

**从哪拿**：

- **应用日志**——默认在数据目录的 `logs/` 下，主文件 `vanehub.log`。各平台路径见[故障排查 → 日志在哪](troubleshooting.md#日志在哪)。
- **会话内日志与链路**——工作区的**日志**、**链路**标签页，见[可观测性](observability.md)。
- **CLI 版本**——`claude --version` / `codex --version` / `gemini --version` / `opencode --version` / `agy --version`。

## 提交前一定要脱敏

**这是必勾项，也是最容易翻车的一步**。

VaneHub AI 落盘的日志已经做过脱敏——provider 密钥、Bearer 令牌、私有路径、命令参数会被替换成脱敏标记。**但截图不会**，你手工粘贴的片段也不会。

提交前逐项检查：

- **凭据**——API Key、token、Cookie、账号密码
- **个人数据**——邮箱、真实姓名、组织名
- **本地路径**——`C:\Users\你的名字\...`、`/home/你的用户名/...`
- **对话内容**——你和 Agent 说过的话、Agent 读到的源码

> **一旦提交就是公开的**。GitHub Issue 对所有人可见，事后编辑或删除都无法收回已经被抓取、被索引或已发出的通知邮件。有疑问就先删掉再提交。

如果日志里的信息因为脱敏而不足以说明问题，可以临时在**设置 → 执行可观测性**把采集策略切到「脱敏内容」再复现一次，见[可观测性](observability.md)。

## 提功能建议

Feature 表单不问版本和复现步骤，问的是另外四件事：

| 字段 | 要点 |
| --- | --- |
| **问题或机会** | 这解决的是什么**用户需求**，不是「我想要什么功能」 |
| **期望结果** | 描述期望的**行为**，**不要假定某种实现方式** |
| **考虑过的替代方案** | 选填，但写了会显著提高被采纳的概率 |
| **补充上下文** | 选填 |

两个必勾项也值得先知道：

- **搜过已有 Issue 和 OpenSpec 变更**——不只是 Issue，还包括仓库里已在推进的规范变更。
- **理解实现需要一份被接受的 OpenSpec 提案**——本项目任何新功能或架构调整都要先走提案流程，Issue 被接受不等于会立刻开工。

## 什么样的 Issue 处理得快

- **一个 Issue 只报一件事**。三个问题写在一起，只会一起卡住。
- **标题写现象，不写猜测**。「升级后 CLI 版本号未刷新」好过「CLI 管理模块有 bug」。
- **区分「必须修」和「可以改进」**，就像评审那样。
- **说明是否稳定复现**。偶发问题也值得报，但要写明是偶发的、大概多久出现一次。
- **附上你已经排除了什么**。「重启过、刷新检测过、换过项目目录，现象不变」能省掉整轮问答。
