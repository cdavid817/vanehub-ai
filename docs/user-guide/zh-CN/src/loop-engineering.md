# Loop 工程化：让 Agent 自己迭代到达成

**状态：已交付——仅桌面端。**

## 功能概述

给定一个目标和一组**必过检查**（例如 `npm run lint` 和 `npm test`），Loop 会驱动 Agent 反复「执行 → 验证 → 判定」，直到目标达成或触及上限。

它解决的是「改完要跑测试，测试挂了要再改」这种反复循环的手工成本。

与[多 Agent 群聊](multi-agent-workflow.md)的区别：群聊是会话内的发言权流转，由 Agent 自己决定交给谁；Loop 是**目标驱动的自动循环**，由运行时按阶段推进并强制执行各项限额。

## 创建一个 Loop

1. 在左侧活动栏选择**循环工程**。
2. 新建定义，填写**目标**——要达成什么。
3. 设置**限额**：
   - 迭代上限（**必须在 1–20 之间**）
   - 单步超时与总超时（总超时不得小于单步超时）
   - 连续运行错误、连续无进展的容忍次数
4. 添加**验收命令**，即必过检查。这些是客观标准。
5. 保存并启动。

## 一次迭代的五个阶段

每轮按固定顺序推进：**准备 → 行动 → 验证 → 判定 → 收尾**。

判定环节按严格优先级短路：

| 顺序 | 条件 | 结果 |
| --- | --- | --- |
| 1 | 命中硬性终止原因 | 按原因归入完成待验收 / 已取消 / 失败 |
| 2 | 校验方给出「阻塞」 | 失败 |
| 3 | **必过检查未全过** | 进入下一轮 |
| 4 | 校验方要求「再改一轮」 | 进入下一轮 |
| 5 | 以上都不成立 | 转入**待人工验收** |

**必过检查排在校验方建议之前。**客观的确定性检查压过主观判断——校验方说「可以了」但 lint 还挂着，照样得改。

## 强制人工验收

**这是 Loop 最重要的一条安全设计：自动循环永远不会自己宣布成功。**

即使判定为「目标已达成」，运行也只会进入**待验收**状态，附带说明「目标达成仍需人工确认」。你不确认，它就停在那里。

## 无进展检测

Loop 会比对每轮的目标状态，识别「原地打转」。**只要满足下面任意一条就算有进展**：

- 代码变更有实质改动
- 失败的检查换了一批
- **某项之前没过的检查现在过了**

第三条尤其有用：假设某轮只修好了 lint、没动别的文件，代码变更可能和上一轮一样，但「新通过了一项检查」会被识别为真实进展。

只有三个维度**全都没变化**，且连续次数达到你设定的容忍值，才会以「无进展」终止。

## 检视执行过程

| 想看什么 | 去哪 |
| --- | --- |
| 各轮阶段流转 | 时间线视图 |
| 单轮的动作与检查结果 | 迭代详情 |
| 整体运行状态 | 运行控制条 |

运行控制条同时提供**暂停**、**取消**。

## 注意事项与限制

- **仅桌面端可用**，依赖本地进程执行验收命令与 Git。
- **迭代上限硬性封顶 20**，无法通过配置突破。
- **必须人工验收**——无人确认时运行会一直停在待验收状态。
- **Loop 在独立的 Git worktree 中作业**，不污染主工作区；因此它**不适用于远程工作区**（远端不支持 worktree）。
- **无进展检测可被「假变化」绕过**：如果每轮都产生无意义但不同的代码变更，检测不会触发。
- 应用完全退出后，运行中的 Loop 不会继续；重启后会对中断的运行做对账。
